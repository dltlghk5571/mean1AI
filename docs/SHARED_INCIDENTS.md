# 공통 현장 사건 관리

담당자가 확인한 여러 민원을 하나의 현장 업무에 연결하는 로컬 시연 기능이다. AI 서버와
외부 지도 없이 동작한다. 개별 민원의 접수일·긴급도·배정·검토·답변은 각 민원에서 관리한다.
현장 상태를 `현장 조치 완료`로 바꿔도 연결된 민원을 자동 종결하거나 답변을 공개하지 않는다.

## 사용 순서

1. 같은 합성 장소의 가로등 고장 등 생활 민원 두 건을 접수한다.
2. 담당자 민원 상세 → **유사 민원 후보** → **중복 후보로 확인**을 누른다.
   확인 전에 **같은 사건 비교**에서 선택적 [LLM 비교 제안](INCIDENT_COMPARISON.md)을 참고할 수 있다.
3. **사건 연결 검토**에서 두 민원의 시설·발생 시점·현재 상황을 대조한다.
4. 둘 다 미연결이면 담당자용 사건 이름과 검토 사유를 적고 확인란을 선택해 사건을 만든다.
   한 건이 이미 사건에 속해 있으면 같은 화면에서 나머지 한 건을 그 사건에 연결한다.
5. **공통 현장 사건** 메뉴에서 사건별 연결 민원 수와 현장 진행을 확인한다.
   `진행 중`은 연결 민원이 있는 미완료 사건, `전체`는 완료·빈 사건까지 보여준다.
6. 검토 승인 계정은 현재 상태와 시민용 문구를 확인하고 **공통 안내 공개**를 누른다.
   연결된 민원의 조회 권한을 가진 시민만 자기 민원 상세의 **현장 진행 안내**에서 확인한다.
7. 오연결은 사건 상세 → 해당 민원 → **이 민원 분리**에서 사유를 남겨 해제한다.
   공통 안내 자체가 잘못되었다면 **공통 안내 공개 철회**로 숨길 수 있다.

`연결 민원 N건`은 접수 기록의 수이며 고유 제보 인원 수가 아니다. 기존 사건 전체를 합치는
기능은 제공하지 않는다. 서로 다른 사건에 속한 두 민원은 필요한 한 건을 먼저 분리한 뒤 검토한다.

## 범위와 역할

| 항목 | 현재 동작 |
| --- | --- |
| 후보 확인 | 기존 분야·정규화 위치·30일·문구 점수 기반 후보를 담당자가 확인 |
| 연결 | 확인된 후보 쌍만 연결; 가로등·도로·청소·공원·교통·상하수도 분야 |
| 제외 | 복지 등 개인별 판단 분야, 기존 정책 검사의 자격·허가·처분·배상 신호, 장소 누락 |
| 혼합 민원 | 한 민원당 공통 사건 한 개. 여러 문제·개인별 요구가 섞이면 연결 전 개별 검토 |
| 재발 | 완료된 사건에는 새 민원을 연결하지 않음. 이전 조치와 새 발생 사실을 사람이 확인 |
| 변경 권한 | `triage.demo`, `review.demo`: 연결·분리·현장 상태 변경 |
| 공개 권한 | `review.demo`: 공통 안내 공개·철회 |
| 읽기 권한 | `audit.demo`를 포함한 담당자 계정: 목록·상세·변경 이력 조회 |

정책 검사와 확인란이 실제 시설 동일성이나 개인정보 부재를 자동으로 증명하지 않는다.
같은 주소의 다른 시설, 새 피해, 해결 후 재발, 긴급 신호를 사람이 직접 대조한다.
미확인 후보·연결 실패는 시민의 새 민원 접수 경로를 막지 않는다.

## 시민 공개

시민 화면에는 명시적으로 공개한 **현장 상태·공통 안내·공개 시각**만 전달한다.
내부 사건 이름·식별자·연결 수·담당자·검토 사유, 타인의 민원 존재·제목·접수번호·주소·사진은
전달하지 않는다. 공개 문구는 담당자가 따로 작성하며 전화번호·이메일·주민등록번호 형식을
거부한다. 기타 식별 내용도 담당자가 검수한다. HTML은 텍스트로 이스케이프해 표시한다.

본인 세션 또는 기존 접수번호·조회 코드 권한을 먼저 확인하며, 공개 사건 검색 목록은 없다.
**연결·분리·현장 상태 변경은 기존 공통 안내를 숨긴다.** 변경된 구성과 상태를 다시 확인해
공개해야 한다. 분리된 민원은 이후 그 사건의 안내를 볼 수 없다. 개별 승인 답변에는 영향이 없다.
문자·이메일·정부 시스템 전송이나 MCP에 비공개 사건을 제공하는 동작도 없다. 선택적 LLM 비교를
활성화하면 담당자가 선택한 두 민원의 재마스킹한 일부 필드와 현장 상태만 설정한 모델에 전달한다.
내부 사건 제목·전체 구성·시민 정보·사진은 전달하지 않는다. 기본 설정은 미연결이다.

## 저장·동시성

- `Incident`: 내부 사건 이름, 분야, 현장 상태, 단조 증가 `revision`.
- `ComplaintIncidentLink`: 현재 연결. `complaint_id` 기본 키로 한 민원의 이중 연결 방지.
- `IncidentEvent`: 변경별 구성·현장 상태·담당자·사유, 공개 작업의 문구 스냅샷.
  `(incident_id, revision)` 고유 제약과 SQLite UPDATE/DELETE 금지 트리거를 적용한다.
- 모든 변경은 영향받은 개별 민원에도 `AuditEvent`를 남긴다. 민원 감사에는 원문·연락처·
  공개 문구를 복사하지 않고 사건 ID·버전·상태·연결 수·정책 버전만 기록한다.

사건 쓰기는 새 세션 트랜잭션에서 `BEGIN IMMEDIATE`를 먼저 실행한다. 빈 연결의 동시 생성까지
직렬화하고, 폼의 `revision`을 DB의 최신 값과 비교한다. 한 트랜잭션에서 연결·사건·이력·감사를
함께 커밋하며 감사 저장이 실패하면 모두 롤백한다. 재전송은 이미 연결됨/버전 충돌로 거부하여
이중 사건·공개 이력을 만들지 않는다. 성공 응답이 유실되면 현재 사건을 조회해 결과를 확인한다.

시민 조회는 현재 연결과 공개 이벤트의 버전이 맞는지 한 SQL 조회로 확인한다. 담당자·시민
화면은 `no-store`를 사용한다. 검토 폼은 실패 시 현재 입력을 유지하고 15초 후 미확인 결과를
안내한다. 최신 버전 충돌은 새로고침해 변경 내용을 재검토해야 한다. 페이지를 떠난 뒤 미전송
검토 문구를 자동 복구하지 않는다.

기존 SQLite 파일은 앱 시작 시 세 개의 추가 테이블과 이력 보호 트리거를 생성한다.
현재 쓰기 구현은 SQLite 전용이며 PostgreSQL 전환 시 잠금·마이그레이션을 다시 구현해야 한다.
사건당 연결은 시연 범위에서 최대 100건, 목록·변경 이력은 페이지당 20건이다.

## 경로와 입력

| 경로 | 용도 |
| --- | --- |
| `GET /staff/incidents?state=active|all&page=1` | 담당자 사건 목록 |
| `GET /staff/incidents/prepare?complaint_id=…&candidate_id=…` | 두 민원 비교·연결 검토 |
| `GET /staff/incidents/{id}?event_page=1` | 구성·진행·공개·변경 이력 |
| `POST /staff/incidents/create` | 이름·두 민원 ID·사유·확인으로 새 사건 생성 |
| `POST /staff/incidents/{id}/linked` | 미연결 `complaint_id`와 기존 구성원 `candidate_id` 연결 |
| `POST /staff/incidents/{id}/unlinked` | `complaint_id` 분리 |
| `POST /staff/incidents/{id}/status_changed` | `status=checking|in_progress|resolved` |
| `POST /staff/incidents/{id}/published` | `message` 5~2,000자, 현재 상태와 함께 공개 |
| `POST /staff/incidents/{id}/withdrawn` | 공통 안내 공개 철회 |

담당자 세션·CSRF가 필요하다. 변경 요청에는 `revision`, 모든 쓰기에는 `reason` 5~500자와
`confirm=yes`가 필요하다. 신규 이름은 2~120자다. 기본 폼은 URL 인코딩, 향상된 UI는 문자열
값으로 구성한 JSON을 전달하며 `Accept: application/json`이면 `redirect` 또는 `message`를
받는다. 버전 충돌은 409, 권한은 403, 잘못된 값은 400/422다. 독립적인 외부 연계 API가 아니라
담당자 웹 화면의 내부 계약이다.

## 검증과 남은 범위

`tests/test_incidents.py`는 생성·연결·분리·진행·공개·철회, 개인별 판단 차단, 역할·CSRF,
타인 민원 차단, 버전 충돌·동시 생성/공개, 감사 실패 롤백과 이력 변경 금지를 검사한다.
`browser_tests/test_incidents.py`는 실제 폼 연결·공개·분리, 모바일 폭, 실패 시 입력 보존을 검사한다.

LLM 같은 사건 비교의 [HTTP 계약·검토 화면](INCIDENT_COMPARISON.md)은 준비했다. 실제 모델
연결·평가, 승인된 좌표/시설 색인, 한 민원 내 여러 문제별 연결, 완료 후 재발 사건 간
관계, 자동 알림, 실제 공무원·시민 사용성 평가는 후속 범위다. 자동 검사를 실제 사용성 결과나
공무원 업무시간 감소 수치로 제시하지 않는다.
