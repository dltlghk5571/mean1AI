# 시민 중심 민원 서비스 설계안

상태: 사용자 승인 후 1차 구현 완료(2026-09-05). 시민 접수·비공개 조회·담당자 답변 공개를
연결했습니다. 실제 행정 시스템 연계는 후속 범위입니다.

## 1. 서비스의 중심

첫 화면은 시민이 생활 속 불편을 제출하는 공간입니다. 담당자 업무 화면은 별도 경로로
분리합니다. 시민에게 담당 부서 선택, 분류 신뢰도, 감사 로그 같은 내부 업무를 요구하지
않습니다. 시민은 불편한 내용을 설명하고, 접수 여부와 자신에게 공개된 결과를 확인합니다.

저장소는 로컬 시연용 프로토타입입니다. 실제 성남시 접수 시스템으로 오해하지 않도록
시연 안내를 유지하고 합성 예시로 전체 흐름을 검증합니다.

## 2. 화면과 경로

| 화면 | 구현 경로 | 시민이 하는 일 |
| --- | --- | --- |
| 시민 메인 | `/` | 민원 신청 또는 내 민원 조회 시작 |
| 민원 작성 | `/minwon/new` | 제목·내용·발생 장소를 입력하고 제출 전 확인 |
| 접수 완료 | `/minwon/{id}/receipt` | 접수 번호와 조회 방법 확인 |
| 내 민원 조회 | `/minwon/lookup` | 접수 번호와 조회 코드로 본인 민원 확인 |
| 내 민원 상세 | `/minwon/{id}` | 접수 내용·진행 상태·공개된 답변 확인 |
| 담당자 업무 홈 | `/staff` | 기존 분류·검토·승인 업무 수행 |
| 담당자 로그인 | `/login` | 담당자 인증 후 `/staff`로 이동 |

동일 브라우저의 유효한 시민 세션에서는 본인이 접수한 목록을 바로 보여줍니다. 세션이
없거나 다른 기기에서는 접수 번호와 조회 코드로 접근합니다. 번호만으로 조회할 수 없습니다.

## 3. 시민 메인

### 첫 화면에서 보이는 요소

- 상단: 서비스 이름, `민원 신청`, `내 민원 조회`, 작은 `담당자 로그인` 링크.
- 안내: 실제 행정기관과 연결되지 않은 시연 서비스임을 짧게 표시.
- 핵심 문구: **우리 동네 불편, 편하게 알려주세요.**
- 보조 문구: 장소와 불편한 내용을 알려주시면, 담당자가 확인할 수 있도록 정리합니다.
- 주요 버튼: `민원 신청하기`.
- 보조 버튼: `내 민원 조회`.
- 빠른 시작: 도로·보도 / 가로등 / 청소·쓰레기 / 공원·시설 / 기타 생활불편.
  선택하면 작성 화면의 도움말을 맞추며 담당 부서나 실제 민원 내용을 임의로 확정하지 않습니다.
- 간단한 절차: `내용 작성 → 담당자 확인 → 결과 확인`.
- 하단: 작성 방법, 조회 방법, 시연 서비스 안내를 펼쳐 읽을 수 있는 도움말.

큰 통계 카드, 민원 전체 목록, 분류 결과와 감사 이력은 시민 메인에 두지 않습니다.
데모 데이터와 실제 조직·정책을 혼동하게 하는 공식 문장·처리 실적·가상 통계도 넣지 않습니다.

### 화면 배치

데스크톱에서는 왼쪽에 핵심 문구와 신청 버튼, 오른쪽에 접수 흐름을 표현한 단순한
일러스트를 둡니다. 그 아래 분야별 빠른 시작과 이용 방법을 배치합니다.
모바일은 핵심 문구 → 신청·조회 버튼 → 분야 선택 순서로 이어져 신청 동작이 먼저 보입니다.
장식 때문에 첫 신청 버튼이 화면 아래로 밀리지 않게 합니다.

기존 민트·화이트 색상은 이어 쓰되, 시민 화면은 넓은 여백과 쉬운 문장, 큰 입력 요소를
중심으로 구성합니다. 담당자 사이드바는 사용하지 않습니다.

## 4. 민원 작성

한 페이지 안에서 `내용 작성 → 제출 전 확인`의 두 단계로 진행합니다.

| 항목 | 필수 여부 | 설계 |
| --- | --- | --- |
| 민원 제목 | 필수 | 한 문장 요약, 2~200자 |
| 불편한 내용 | 필수 | 언제·어디서·무엇이 불편한지, 5~20,000자 |
| 발생 장소 | 선택 | 주소 또는 주변 시설을 글로 입력, 최대 300자 |
| 분야 | 선택 | 작성 도움말을 위한 선택. 실제 분류는 기존 분석·검토 과정에서 결정 |
| 시연 안내 확인 | 필수 | 합성 예시만 입력하고 실제 행정기관 접수가 아님을 확인 |

- 연락처·주민등록번호·실명은 1차 시연 화면의 필수 입력 항목으로 만들지 않습니다.
- 작성란 아래에 실제 개인정보 입력을 피하도록 안내하고, 제출 전에는 비식별 내용을 확인합니다.
- `합성 예시로 체험`은 사용자가 명시적으로 선택할 때만 입력됩니다. 예시가 실제 민원인 것처럼
  채워진 상태로 시작하지 않습니다.
- `다음: 내용 확인`에서 요약을 보여주고 `수정하기` 또는 `민원 제출하기`를 선택합니다.
- 내용 확인을 위해 서버를 호출하더라도 이 단계에서는 민원을 저장하거나 AI를 실행하지 않습니다.
- 제출은 실제 서버 접수 성공 후에만 완료로 표시합니다. 재전송은 같은 접수 요청으로 처리합니다.
- 실패하면 작성 내용을 현재 화면에서 유지하고 재시도 방법을 안내합니다. 본문을 URL이나
  브라우저 영구 저장소에 기록하지 않습니다.
- 긴급 위험 표현은 제출 과정에서 기존 안전 정책으로 검사합니다. 화면 안내가 실제 긴급 신고를
  대신하지 않으며 담당자 긴급 확인 흐름으로 연결합니다.
- 입력 영역과 하단 동작 영역을 분리해 모바일에서도 제출 버튼을 사용할 수 있게 합니다.

## 5. 접수 완료와 조회

### 접수 완료

**민원이 접수되었습니다.**라는 확인과 다음 내용을 보여줍니다.

- 접수 번호, 접수 시각, 비식별 제목.
- 조회 코드와 `접수 정보 복사` 동작. 코드는 주소창에 넣지 않습니다.
- `접수한 민원 보기`, `홈으로 돌아가기` 버튼과 상단의 `민원 신청` 링크.
- 실제 기관으로 전송되지 않은 데모 접수이며 담당자 검토가 다음 단계라는 설명.

조회 코드는 접수 완료 시 안내하고, 서버에는 원문 대신 검증용 해시를 저장합니다.
접수 번호는 공유 가능한 식별자이고 조회 코드는 접근 수단이라는 차이를 분명히 안내합니다.
시연 단계에서 코드를 잃은 경우의 한계도 조회 화면에 설명합니다.
원래 브라우저의 유효한 소유 세션에서는 접수 확인서를 다시 열어 동일 코드를 볼 수 있습니다.
조회 코드로 새 접근 권한만 받은 브라우저에는 원래 코드가 표시되지 않습니다.

### 내 민원 상세

상단에는 제목·접수 번호·현재 상태를, 아래에는 진행 흐름·제출 내용·답변 영역을 배치합니다.
AI의 내부 추론, 부서 후보 순위, 신뢰도, 다른 사람의 민원, 담당자의 계정·감사 기록은
이 화면의 표시 대상으로 삼지 않습니다.

| 시민에게 보이는 상태 | 실제 의미 |
| --- | --- |
| 접수 완료 | 접수 내용과 조회 권한이 정상 저장됨 |
| 확인 중 | 담당자 확인을 기다리거나 내부 검토 중 |
| 답변 등록 | 담당자가 시민에게 공개할 답변을 명시적으로 확정함 |

`AI 분류 완료`를 민원 처리 완료로 표현하지 않습니다. 기존 `내부 검토 완료`도 답변 공개나
민원 종결로 간주하지 않습니다. 기존 승인 기능과 별도로 `시민 화면에 답변 공개` 동작과
공개 답변의 고정된 버전이 필요합니다. 공개 전 초안은 시민 화면에 표시하지 않습니다.

답변이 아직 없으면 다음 단계와 현재 상태만 안내합니다. 정해지지 않은 처리 기한·처리 결과를
약속하거나 진행률을 만들어 표시하지 않습니다. 공개 이후 수정은 새 버전과 이력으로 기록합니다.

## 6. 기존 기능과 연결

시민 접수도 기존 개인정보 비식별 → 긴급·민감 정책 → 분류 → 근거 검색 → 초안 생성
흐름으로 들어갑니다. 접수된 민원은 담당자 `/staff` 대기열에 나타나야 합니다.
시민 화면에서 새로 분류 엔진을 만들거나 안전 판단을 우회하지 않습니다.

필요한 설계 변경은 다음으로 제한합니다.

- 시민 소유권·조회 권한: 민원과 소유 세션, 조회 코드 해시, 접수 시각을 연결.
- 중복 접수 방지: 제출 요청 식별자를 저장해 재시도와 중복 클릭을 같은 접수로 처리.
- 답변 공개 기록: 공개 권한을 가진 담당자, 공개 시각, 해당 답변 버전을 별도로 기록.
- 시민 접수와 소유권·감사 기록은 함께 성공하거나 함께 실패하도록 저장 경계를 정리.
- 시민 화면의 필요한 경로만 허용하고 기존 `/api/v1/complaints`, 감사·승인·재분석 경로의
  담당자 인증과 역할 검사는 유지.
- 시민용 쿠키·CSRF 검증은 담당자 세션과 분리. 쿠키를 지우거나 기기를 바꿔도 조회 코드를
  통한 제한된 재접근이 가능하도록 구성.
- 잘못된 조회 번호·코드는 같은 안내를 반환하고 시도 횟수를 제한. URL 변경으로 타인 민원에
  접근할 수 없는지 검증.
- 개인정보가 포함될 수 있는 응답에는 캐시 방지 정책을 적용하고 입력 내용을 로그에 남기지 않음.

## 7. 1차 구현 범위

시민 메인, 작성·제출 전 확인, 접수 완료, 내 민원 조회·상세, 담당자 대기열 연결,
시민 공개 답변의 권한·이력까지를 한 흐름으로 완성합니다.

사진 첨부, 지도 선택, 실명 인증, 문자·이메일 알림, 실제 행정 시스템 연계는 후속 범위입니다.
구현하지 않은 기능을 동작하는 버튼처럼 배치하지 않습니다.

## 8. 구현 후 수용 기준

1. 로그인하지 않고 `/`에 들어오면 시민 메인이 보이고 곧바로 작성을 시작할 수 있음.
2. 시민이 제출한 민원이 담당자 대기열에 한 번만 나타남.
3. 접수 완료 화면은 DB 저장 성공 이후에만 표시됨.
4. 다른 브라우저에서 번호만 입력하거나 URL만 바꿔 타인의 민원·초안·감사 정보에 접근할 수 없음.
5. 내부 승인만으로 시민 답변이 자동 공개되지 않음. 명시적으로 공개한 답변만 조회 가능.
6. 긴급·민감 민원의 사람 검토와 모든 감사 기록이 기존 규칙대로 유지됨.
7. 빈 값·입력 오류·접수 실패·조회 실패·답변 대기 상태에 실제 사용할 수 있는 안내가 있음.
8. 390px 모바일에서 작성·확인·제출·조회 버튼이 잘리지 않고 키보드만으로도 진행할 수 있음.
9. 기존 담당자 권한·CSRF·감사 이력과 오프라인 규칙 제공자 테스트가 통과함.

구현 파일은 `app/api/citizen.py`, `app/services/citizen.py`, `citizen_*.html`,
`citizen.css`, `citizen.js`입니다. 소유권·세션·조회 권한·공개 답변은 새 테이블로 추가해
기존 민원 데이터를 변경하지 않습니다. 상세 접근 정책은 `AUTH_AND_AUDIT.md`,
화면 사용성과 검증 절차는 `UI.md`, 회귀 테스트는 `tests/test_citizen.py`에 정리했습니다.
