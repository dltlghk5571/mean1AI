# 수집 보고서 확인 화면

2026-09-11 · 입력: 추출 보고서 v2 · 화면 응답·확인할 일 내보내기: v1

`/staff/source-reports`에서 수집기의 JSON을 읽고 누락·중복·부서 표기 차이를 확인한다.
AI 서버가 필요 없으며, 보고서를 열어도 수집·카탈로그 등록·공개 승인을 실행하지 않는다.
이 화면은 자료 검수 전의 근거 확인 도구다. 실제 부서와 정책을 확정하는 절차는
[등록·승인 계약](SERVICE_DATA_PIPELINE.md)에 있다.

## 화면에서 확인하기

1. 로컬 앱을 실행하고 담당자 계정으로 로그인한다. 공개된 시연 계정은
   `review.demo` / `review-demo-2026`이다.
2. 왼쪽 메뉴에서 **수집 결과 확인**을 연다. **합성 예시로 살펴보기**는 실제 정책이 없는
   목록 2개·상세 1개의 예시를 보여준다. 누락된 상세와 본문/하단 부서 차이를 확인할 수 있다.
3. **JSON 파일 선택**으로 [수집기](SEONGNAM_COLLECTOR.md)가 만든 UTF-8 보고서 v2를 연다.
   파일 하나당 최대 8,000,000바이트다. `ServiceBundle`이나 확인할 일 내보내기 파일은 입력이 아니다.
4. **누락·오류 / 부서 표기 / 중복·변경 / 출처·정책**을 골라 확인한다. 업무명·부서명·원본 번호로
   검색할 수 있다. 확인할 일은 12개씩, 목록 항목·팀별 업무 행은 25개씩 펼쳐 볼 수 있다.
5. **페이지 근거 보기**나 페이지 선택 상자로 본문·목록·팀별 업무를 대조한다. 복지 상세의 본문
   문의처와 하단 부서 표시는 따로 보여준다. 연도는 본문에 등장한 숫자이며 시행일이 아니다.
6. **확인할 일 내려받기**로 전체 확인 항목을 JSON으로 받는다. 현재 필터에 관계없이 전체를
   내보낸다. 완료 표시나 담당자 메모 저장 기능은 없다. **보고서 닫기**와 새로고침은 화면을 비운다.

입력은 로그인한 앱 서버로 전송되어 메모리에서 검사된다. 브라우저 안에서만 처리하는 기능은
아니다. 서버는 파일·본문·검수 결과를 DB나 파일에 저장하지 않으며 응답은 `Cache-Control: no-store`다.
네트워크 수집, 외부 URL 자동 조회, AI 호출, `ServiceCatalogReview` 기록은 발생하지 않는다.
다운로드한 JSON은 사용자가 선택한 컴퓨터에 남는다.

## 검사 결과 읽기

| 표시·검사 | 의미 |
| --- | --- |
| 다시 계산한 결과 안내 | 파일에 적힌 집계·완결 여부·남은 링크와 페이지 근거의 재계산 결과가 다름. 재계산 값을 표시하며 원본을 다시 대조해야 함 |
| 추출·대조 조건 충족 | 확보한 입력 범위의 완결 조건만 충족. 이용 조건·정책·실제 관할 검수와 공개 승인은 여전히 필요 |
| 파일 SHA-256 | 업로드한 원본 JSON 바이트의 식별값. 공백·줄바꿈을 바꾸어도 달라짐 |
| 페이지 입력 SHA-256 | 보고서에 기록된 HTML/DOM 입력 해시. 화면에는 원래 입력 파일이 없어 재계산할 수 없음 |
| 본문 검증 | 문서 본문의 SHA-256, 페이지와 문서 참조·출처·종류, 기록 수와 입력 모드를 검사 |
| 합성 예시 | 실제 출처로 오해하지 않도록 원본 사이트 링크를 제공하지 않음 |

등록된 출처와 URL 범위, 스키마와 값의 타입·상한, 직접 식별자 형식을 검사한다. 알 수 없는
필드·중복 JSON 키·손상된 참조·본문 해시 오류를 거부한다. 마스킹 전 전화번호·이메일·주민번호
형식이 남으면 원문을 응답에 포함하지 않고 오류 코드만 반환한다. 사람 이름이나 모든 개인정보를
탐지하는 기능은 아니므로 실제 민원 원문을 넣지 않는다.

누락·중복·목록/상세 차이는 입력 근거로 다시 계산하며, 삭제된 검토 사유 중 본문 연도·문의처
차이·반복 업무처럼 다시 확인할 수 있는 조건도 복원한다. **보고서의 진위나 원본 사이트의
현재 내용과 일치함을 보증하지 않는다.** 원래 HTML 없이 목록·문의처·하단 부서의 추출 정확성을
재검증할 수는 없다. 조직도 누락은 등록한 7개 코드의 범위이며 성남시 전체 조직 검사도 아니다.
이용 조건은 추출 보고서의 `unknown` 상태만 허용한다. 수집 보고서에 승인 값을 써 넣어 공개할 수 없다.

오류가 나면 이전 결과를 숨기고 재선택할 수 있게 한다. 화면 요청 제한은 20초이며 파일 입력을
초기화하므로 같은 파일로 다시 시도할 수 있다. 로그인 만료·크기 초과·형식 오류는 화면에서 안내한다.

## 팀 전달물과 API

수집 담당 C는 원본 보고서와 적법하게 확보한 HTML/DOM 근거를 관리한다. 데이터 담당 A는
확인할 일 JSON을 받아 [검수 작업표](SEONGNAM_DATA_REVIEW.md)에 판단과 근거를 기록하고,
수집 보완이 필요한 항목을 C에게 전달한다. UI 담당 B는 키보드·작은 화면에서 검수 과제를 확인한다.
모델 담당 D에게는 사람이 검수한 업무 ID·질문·검색 자료를 전달한다.

확인할 일 JSON에는 `schema_version`, `report_sha256`, `source_id`, `review_status=pending`,
`exported_at`, `pages`, `tasks`가 있다. 페이지 참조에는 번호·제목·원본 코드·URL·입력 해시가,
각 확인 항목에는 종류·사유·페이지 참조·`status=pending`이 있다. 파일 해시로 원본 보고서와
연결한다. 본문 전체·필터 상태·승인 결과는 포함하지 않는다. 이 파일을 검수 화면에 재등록하거나
시민 검색 자료로 바로 사용하지 않는다. 검수한 업무를 별도 `ServiceBundle`로 구성한다.

| 경로 | 권한·결과 |
| --- | --- |
| `GET /staff/source-reports` | 로그인한 담당자의 화면 |
| `GET /api/v1/source-reports/example` | 담당자 세션, 합성 예시를 검사한 화면 응답 |
| `POST /api/v1/source-reports/preview` | 분류 담당·검토 승인·감사 조회 역할과 CSRF 헤더, JSON 원문 검사 |

POST는 `Content-Type: application/json`, `X-CSRF-Token`을 요구한다. 조회용 검사이므로 감사 조회
역할도 사용할 수 있지만 카탈로그 등록 권한이 생기지는 않는다. 응답은 `schema_version=1`,
`persisted=false`, `review_status=pending`, `summary_matches`, `completed`, `summary`, `pages`,
`tasks`를 포함한다. 크기 초과는 413, JSON 이외 형식은 415, 내용 검증 실패는 422다.

## 검증과 남은 확인

자동 테스트는 입력 손상·식별자·URL·참조·집계 재계산, 인증·CSRF·역할, 크기 제한,
검사 후 카탈로그와 검수 이력이 바뀌지 않는 조건을 검증한다. 실제 AI 서버나 공식 사이트 없이 실행한다.
전체 pytest 560개, Ruff·mypy, rules 228건·RAG 36건과 합성 평가셋 100건 계약 검증을 통과했다.

브라우저에서 합성 응답으로 오류 복구·집계 차이·검색과 필터·긴 목록·본문의 HTML 문자 표시를
확인했다. 320px 화면의 가로 넘침과 페이지 근거 제목의 상단 메뉴 가림도 수정 후 재확인했다.
대화 도구의 파일 연결과 Windows 앱 실행 승인 단계에서 지연이 발생해 기본 파일 대화상자의
수동 조작 검증은 완료하지 못했다. 이를 대신할 회귀 검사로 아래의 격리된 Chromium 테스트를
추가했다. OS 파일 대화상자의 폴더 탐색·파일 지정 조작은 실제 팀원이 별도로 확인한다.

## 파일 흐름 자동 검사

일반 API 테스트는 `pytest`, 브라우저 검사 3개는 `pytest browser_tests`로 분리한다.
후자는 화면의 파일 입력과 키보드 Enter/라벨 클릭, FileChooser, 실제 POST, 화면 결과,
Blob 다운로드 파일의 JSON까지 연결한다. 서버 응답을 가짜 결과로 바꾸지 않는다.

| 과제 | 자동으로 확인하는 결과 |
| --- | --- |
| 정상 업로드·내려받기 | 한글·공백 파일명, 업로드 원본 바이트·SHA-256, 부서 비교, 필터가 한 항목이어도 전체 확인할 일·페이지 참조 내보내기, 모두 검수 대기, 같은 파일 재선택 |
| 손상 파일·복구 | 422 후 이전 결과 숨김, 같은 손상 파일 재선택, 집계가 변경된 정상 보고서의 재계산 경고와 화면 복구 |
| 용량·식별자 거부 | 8MB 초과 파일의 서버 전송 차단, 합성 직접 식별자가 포함된 파일의 거부와 원문 미표시, 정상 파일로 복구 |

임시 SQLite·127.0.0.1의 동적 포트·새 Chromium 컨텍스트만 쓴다. 사용자 브라우저, 저장된
로그인 정보나 쿠키에 연결하지 않는다. 앱의 외부 HTTP와 페이지의 외부 요청을 차단하며,
검사 후 카탈로그·승인 이력이 추가되지 않았는지도 확인한다. 파일 선택·응답 대기와 서버 시작에
제한 시간이 있고 성공/실패 후 브라우저·서버를 정리한다. CI 작업 전체의 제한은 10분이다.

```bash
python -m pip install -e ".[dev,browser]"
python -m playwright install chromium
python -m pytest browser_tests
```

`browser` 추가 의존성은 자동 검사용 Playwright뿐이다. 앱 운영·일반 API 테스트에는 필요 없다.
Linux CI는 `python -m playwright install --with-deps chromium`으로 브라우저의 OS 의존성도 설치한다.
실패 시 합성 화면만 `.local/browser-artifacts/`에 저장하고 CI에서 7일간 보관한다. 쿠키·저장소·
사용자 입력 자료는 테스트 산출물에 포함하지 않는다.
[파일 입력](https://playwright.dev/python/docs/input#upload-files),
[다운로드](https://playwright.dev/python/docs/downloads),
[CI 설치](https://playwright.dev/python/docs/ci)의 공식 API를 사용한다.

## 팀원이 한 번 확인할 과제

실제 정책을 넣기 전에 `app/data/collection_report_demo.json`으로 아래 과제를 수행한다.
이는 자동 검사와 별개인 실제 기기 사용성 확인이다. 수행일·브라우저·OS·성공 여부와 막힌 지점을
기록하며 아직 팀원 평가 결과는 없다.

1. **B UI**: Tab으로 파일 선택에 도달하고 Enter로 기본 대화상자를 연다. 취소 시 오류나 기존
   결과 변경이 없는지 확인하고 다시 열어 예시 파일을 고른다.
2. **A 데이터**: 부서 표기 항목을 선택해 본문/하단 차이를 찾는다. 확인할 일을 내려받아
   파일이 존재하고 `review_status=pending`, 항목 6개, 페이지 2개인지 확인한다.
3. **C 서버**: 같은 파일을 다시 열고 새로고침 후 결과가 비워지는지 확인한다. 카탈로그 등록이나
   공개 이력이 생기지 않아야 한다. 실제 원문 수집은 [수집기 조건](SEONGNAM_COLLECTOR.md)을 따른다.
4. **D 모델·평가**: 내려받은 파일이 모델 정답·학습 허용이나 `ServiceBundle`이 아님을 확인하고,
   모델 팀 전달물에는 사람 검수를 거친 업무 ID와 별도의 이용 조건을 연결한다.

실제 스크린리더·모바일 파일 선택과 다운로드 저장 위치의 사용성 평가는 남아 있다.
