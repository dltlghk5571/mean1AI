# 성남시 대화형 민원·생활정보 에이전트 계획

작성일: 2026-09-05 · 갱신일: 2026-09-07 · 팀: 4명 · 상태: 시연 챗봇·사진 접수·검수 자료·도구 실행기 구현

시민이 부서명이나 행정용어를 몰라도 일상적인 말로 시작할 수 있는 서비스를 만든다.
에이전트가 질문의 목적을 파악하고, 공식 정보를 찾아 답하거나 필요한 정보를 추가로 받아
민원 접수 내용을 준비한다. **시민의 진입 화면은 챗봇이며, 핵심은 안내에서 접수·진행 확인까지
끊기지 않는 것**이다.

이 문서는 향후 작업 계획과 조사 자료다. 시연 챗봇 UI·접수 확인·검수 자료·도구 실행기는
구현했으며, 현재 동작하는 범위는 [챗봇 HTTP 계약](CHAT_API.md)과 [도구 JSON v2](AGENT_API.md)를
기준으로 한다. 동아리 대화 모델용 HTTP 어댑터와 담당자 자료 검수 화면도 준비했다.
실제 서버 접속·모델 평가, 실제 부서 카탈로그 교체와 대량 수집은 후속 범위다.
구체적인 분류표와 API·수집 출처는 [분류·데이터 조사 문서](SERVICE_TAXONOMY_AND_SOURCES.md)에 정리했다.

## 1. 현재 구현에서 출발할 수 있는 부분

| 항목 | 현재 상태 | 다음 방향 |
| --- | --- | --- |
| 시민 페이지 | 대화 진입, 내용·장소 질문, 초안 수정·확인·사진 접수, 비공개 조회 구현 | 실제 모델의 추가 질문·검색·사진 판독 연결 |
| 부서·업무분장 | 합성 데모 자료이며 실제 성남시 조직을 반영한 상태가 아님 | 공식 출처로 조사·검수한 부서·업무·관할 자료를 별도 버전으로 구축 |
| 분류 | 기본값은 규칙 방식. LLM 분류 어댑터도 일부 존재 | 운영 분류는 별도 LLM 모델이 담당. 규칙 데모와 평가 기준선은 구분해 유지 |
| 답변·검색 | 승인된 합성 자료에서 검색하고 초안을 검토·공개 | 최신 공식 정책·복지·민원편람으로 검색 자료 확장 |
| 중복 후보 | 분야·위치·시간·문구를 비교하는 규칙 점수와 담당자 검토가 있음 | LLM의 같은 사건 여부 비교, 본인 후속 문의, 공통 현장 업무 연결로 확장 |
| 정부 연계 | 실제 성남시·국민신문고 접수, 본인인증, 문자 연계 없음 | 조회 API부터 연결하고 정식 접수는 기관 협의 후 별도 연결 |
| AI 서버 | 동아리 서버 연결 없음 | 대화 모델과 분류 모델의 인터페이스를 분리하고 주소·모델은 추후 주입 |

현재 LLM 분류 코드는 외부 SDK의 구조화 응답을 사용하는 방식이다. 동아리 서버가 단순히
호환 URL을 제공한다는 이유만으로 그대로 연결된다고 가정하지 않는다. 요청·응답·스트리밍·도구 호출
지원 범위를 확인한 뒤 어댑터를 둔다. 기존 카탈로그는 합성 데이터만 허용하므로 실제 자료 도입 시
로더·검증·테스트와 화면의 데모 표시도 함께 변경해야 한다.

## 2. 실제 페이지에서 확인한 문제와 강조할 가치

국민신문고 신청 진입 화면을 확인했다.

- 민원/제안/신고 목록은 서비스 유형 7개, 분야 8개, 서비스 45건으로 표시됐다.

  게시물 수를 고유 민원 종류 수로 보면 안 된다. 목록의 상위 기관 표시에서 상세 페이지의
  담당 과와 첨부 서식까지 더 탐색해야 하는 사례를 확인했다.
  [민원 편람](https://www.seongnam.go.kr/bbs020405), [분당구 방음시설 대여 상세](https://www.seongnam.go.kr/bbs020405/385620)

  안내와 국민신문고 직접 이동 링크가 있다. 실제 신청 진입은 로그인·본인확인 화면으로 연결됐다.
  [성남시 민원상담](https://www.seongnam.go.kr/pm02020101/40), [국민신문고 신청 진입](https://www.epeople.go.kr/nep/pttn/gnrlPttn/PttnRqstWrtnInfo.paid)

본인인증 이후 신청서의 부서 선택 화면까지 확인하지 않았다. **모든 민원이 수십 개 부서 중 하나를
반드시 직접 선택해야 한다는 주장이나, 45건을 부서 수로 바꾸는 표현은 사용하지 않는다.**

발표에서는 다음 가치로 설명한다.

> 시민이 조직도와 민원 서식을 먼저 이해해야 하는 탐색 부담을 줄이고,
> 자신의 상황을 말하면 필요한 안내·질문·서류 준비·접수로 이어지게 한다.

국민신문고에도 기관 추천 개선과 생성형 AI 활용이 이미 추진돼 왔다. 따라서 “공공 민원에
AI 분류를 처음 적용한다”보다 **성남시의 실제 업무·관할과 연결된 쉬운 대화, 보완자료 준비,
안내와 접수의 구분, 답변 후 조치 확인**을 차별점으로 삼는다.

## 3. 시민의 대화 흐름

| 시민의 말 | 에이전트가 하는 일 | 결과 |
| --- | --- | --- |
| “내가 받을 수 있는 복지혜택 뭐 있어?” | 지역·관심 지원 등 필요한 조건만 묻고 공식 복지 DB 검색 | 근거와 기준일이 있는 안내·신청 경로. 수급 자격을 확정하지 않음 |
| “집 앞 가로등이 며칠째 안 켜져” | 발생 위치와 상황을 확인하고 민원 유형·부서 후보 판단 | 확인 가능한 요약을 만들고 시민 확인 후 접수 |
| “어제 말한 곳인데 아직 그대로야” | 조회 권한이 있는 본인 민원과 진행 기록 확인 | 기존 민원에 추가 의견·조치 확인 요청. 새 민원 자동 중복 생성 방지 |
| “이거 민원인지 그냥 물어볼 일인지 모르겠어” | 원하는 것이 설명인지 현장 조치인지 한 번에 하나씩 확인 | 안내 또는 접수 준비로 자연스럽게 전환 |
| “신청이 거절됐는데 이유를 모르겠어” | 안내 가능한 절차를 검색하고 처분·이의신청에 필요한 전문 검토 구분 | 원문 근거와 담당 창구 안내, 필요하면 사람이 검토할 접수 초안 |

기본 순서는 **자유 입력 → 목적·위험 확인 → 필요한 정보 검색·추가 질문 → 안내 또는 접수 요약 →
접수 확인 → 진행 확인**이다. 한 대화에 복지 질문과 생활민원이 섞이면 각각 분리해 처리하고
무엇이 안내됐고 무엇이 접수될지를 보여준다.

### 자동 접수의 의미

사용자가 별도 긴 서식을 채우지 않아도 에이전트가 제목·내용·위치·필요 자료를 정리한다.
마지막에 요약과 첨부자료를 보여주고 **“이 내용으로 접수” 한 번으로 확정**한다. 시민이 내용을
수정하면 요약 버전을 갱신하고 이전 확인을 재사용하지 않는다. 상담만 하던 내용은 민원으로
자동 등록하지 않는다.

현재 데모에서는 앱 내부 접수번호를 발급한다. 정식 기관 연계 후에는 기관의 수신·접수 응답을
받아 공식 접수번호를 표시한다. 전송 실패·시간초과 중에는 접수 완료라고 표시하지 않으며,
중복 요청 방지 키와 수신 확인으로 재전송을 관리한다.

### 추가 질문과 사진

- 한 번에 한 가지 질문을 기본으로 하고, 이미 말한 내용은 다시 묻지 않는다.
- “주소를 모르겠어요”, “사진이 없어요”, “다른 방법으로 설명할게요” 선택을 제공한다.
- 위치는 지명·시설명·주소 등 가능한 표현으로 받고, 추정 결과는 시민에게 확인한다.
- 사진은 민원 유형과 근거에 따라 도움이 되는 경우 요청한다. 필수 자료인지는 공식 요건으로
  판단하며 LLM이 임의로 필수 서류를 만들지 않는다.
- 사진이 없으면 가능한 대체 설명과 처리 경로를 안내한다. 위험한 장소에서 촬영하도록 유도하지 않는다.
- 현재 시연은 파일 메타데이터를 제거한 JPEG만 비공개 DB에 저장하며 원본은 보관하지 않는다.
  얼굴·차량번호·문서 속 식별정보를 처리할 별도 검토가 필요하므로 모델에 사진을 보내지 않는다.
  [사진 접수 계약](CITIZEN_PHOTOS.md)을 따르며, 사진만으로 장소·위반·책임을 확정하지 않는다.

### 중복·유사 민원과 같은 현장 문제

**개별 시민의 접수 기록을 보존하면서 같은 현장 문제의 처리 업무를 연결한다.** 예를 들어 같은
가로등 고장을 20명이 제보하면 접수·신청인별 답변 기록은 각각 유지하고, 확인된 수리 업무를
한 건으로 묶는다. 접수 건수와 현장 사건 수를 따로 집계해 반복적으로 들어온 신호도 남긴다.

| 상황 | 판단·대화 | 처리 방식 |
| --- | --- | --- |
| 전송 버튼 연타·통신 재시도 | 서버가 같은 제출 요청인지 확인 | 동일 요청에는 기존 처리 결과 반환. LLM 판단 없이 중복 저장 방지 |
| 본인이 같은 문제의 진행을 다시 질문 | 권한이 확인된 본인 기록을 찾아 진행 조회·추가자료·별도 접수 선택 제공 | 사용자가 선택한 기존 민원에 후속 기록을 남기거나 별도 접수 준비 |
| 다른 시민들이 같은 현장 문제 제보 | 장소·시설·발생 시점·현재 상황을 비교 | 각자 접수 후 담당자가 공통 현장 업무 연결 검토. 제보자의 개별 요구·답변 유지 |
| 처리 이후 재발, 새 피해·사진·위험 발생 | 이전 조치와 달라진 사실을 확인 | 재발 사건 또는 추가 사실로 별도 검토. 기존 완료 상태를 그대로 적용하지 않음 |
| 문구는 비슷하나 장소·대상·기간이 다름 | 실제로 같은 사건인지 비교하고 부족하면 질문 | 별도 사건으로 취급하거나 판단 보류 |

복지 자격·허가·개인 분쟁처럼 사람마다 사실관계가 달라지는 신청은 초기 현장 업무 묶음에서
제외한다. 반복적인 정보 질문은 공식 안내 검색으로 답하고 접수 의사가 있는 경우 접수로 이어간다.
제보 횟수만으로 악성 여부나 낮은 우선순위를 부여하지 않으며, 새 긴급 신호는 중복 검색보다 먼저 처리한다.

#### 검색 → LLM 비교 → 서버 검증

1. 서버가 제출 요청 ID와 초안 버전으로 기술적인 재전송을 식별한다. 키는 요청자 권한·작업 범위에
   묶고 같은 키의 내용이 바뀌면 충돌로 처리한다. 본인 확인 없이 이름·전화번호만으로 기록을 연결하지 않는다.
   동시 요청도 DB 고유 제약·트랜잭션으로 한 번만 저장하고, 전송 중에는 완료로 표시하지 않는다.
2. 의미 검색으로 후보를 찾고 위치·시설 ID·발생 시점·해결 상태를 함께 확인한다. 검색 시간 범위와
   거리 기준은 업무별로 검수하며, 같은 문장·같은 주소만으로 사건을 확정하지 않는다. 접수일과 실제
   발생일을 구분하고 누락된 값은 추정 사실로 채우지 않는다.
3. 기존 분류 LLM이 후보별로 `same_incident` / `related_distinct` / `recurrence` / `uncertain`을
   판단하고 일치 근거·차이·추가 질문을 JSON으로 반환한다. 세 번째 생성 모델은 우선 추가하지 않는다.
   임베딩 검색은 후보를 고르는 용도이고, LLM 비교는 개별 사건 관계를 검토하는 용도다.
4. 서버가 후보의 출처·접근 범위·초안 버전을 검사한다. 본인 후속 기록은 시민 선택을 확인하고,
   여러 시민의 현장 업무 연결은 담당자 검토 후 반영한다. 연결 해제·재분리가 가능하게 이력을 보존한다.
5. 후보가 없거나 검색·모델이 실패해도 새 민원 접수를 진행할 수 있다. 결과는 미확인으로 남겨
   사후 검토하며, 점수가 높다는 이유로 자동 반려·종결하지 않는다.

분류 모델의 관계 비교 응답 예시는 다음과 같다. 식별자는 모두 예시이며 서버가 제공한 후보만 선택한다.

```json
{
  "schema_version": "1",
  "draft_version": 3,
  "candidate_set_id": "example-candidate-set",
  "matches": [
    {
      "candidate_ref": "example-candidate-1",
      "relation": "same_incident",
      "evidence_codes": ["same_confirmed_asset", "overlapping_occurrence_time"],
      "differences": [],
      "missing_slots": [],
      "review_required": true
    }
  ]
}
```

`candidate_ref`는 현재 요청에 묶인 비교용 참조이며 타인의 접수번호나 조회 권한이 아니다. 근거
코드는 입력 자료와 대조하고, 확인할 수 없으면 `uncertain`으로 처리한다. 실제 연결·진행 조회·접수
동작은 서버가 권한과 검토 결과로 결정한다. 장소나 상황을 수정하면 후보를 다시 확인한다.

#### 시민 화면과 데이터 접근

본인 민원은 기존 조회 권한이 확인된 범위에서 보여준다. 다른 시민의 비공개 민원은 존재 여부,
내용·사진·주소·접수번호를 대화 모델과 시민 화면에 노출하지 않는다. 외부 제보와의 비교는 별도
승인·비식별 처리된 현장 사건 색인을 사용하는 내부 도구로 제한한다. 공개가 승인된 사건 정보가
있는 경우에만 “이 시설은 점검 중입니다. 공개된 진행 상황을 보거나 추가 제보를 접수할 수 있어요”로
안내한다. 공개 자료가 없으면 정상 접수를 이어가고 연결 검토는 담당자 화면에서 한다.

초기 DB 확장 후보는 공통 현장 업무인 `Incident`와 민원 내 개별 문제를 연결하는
`ComplaintIncidentLink`다. 하나의 민원에 여러 문제가 있으면 문제 단위로 관계를 관리한다.
연결에는 검토 상태·근거·모델/정책 버전·담당자·변경 이력을 기록한다. 각 민원의 최초 접수일,
처리기한, 답변 승인·공개 상태는 보존한다. 현장 작업 완료로 모든 민원을 일괄 종결하지 않으며,
공통 진행 안내를 재사용할 때에도 개별 수신 범위와 공개 승인을 확인한다.

AI 비교와 사람의 연결·해제 판단은 `AuditEvent`에 기록한다. 초기 평가는 서로 다른 가로등·같은
주소의 다른 시설·처리 후 재발·새 긴급 상황·혼합 민원·검색 실패·동시 전송을 포함한다. 후보 검색
누락률과 잘못된 연결률을 따로 평가하고, 타인 정보 노출·자동 반려·기한 소실을 필수 실패 항목으로 둔다.

법적 반복·중복민원 종결은 별도 검토 대상이다. 참고한 [민원 처리에 관한 법률 제23조의
2022-07-12 시행본](https://www.law.go.kr/LSW/lsSideInfoP.do?docCls=jo&joBrNo=00&joNo=0023&lsiSeq=239293&urlMode=lsScJoRltInfoR)에는
법정민원 제외, 정당한 사유, 처리결과 통지 등 요건과 내용·관련성에 대한 종합 판단이 있다.
이 계획의 현장 업무 연결을 그 법적 종결 판단으로 취급하지 않으며, 정식 도입 시 적용일의 법령과
기관 절차를 다시 검수한다.

현재 코드는 규칙으로 중복 **후보**를 만들고 담당자가 검토하는 단계다. 위 LLM 비교, 시민 안내,
현장 사건 색인과 관계 DB는 향후 구현 범위다. A가 사건별 판단 기준, B가 후속 문의·추가 제보 UI,
C가 재전송 방지·색인·접근 제어·업무 연결, D가 관계 비교 프롬프트와 평가셋을 맡는다.

## 4. 대화 모델 1개 + 분류 모델 1개

두 모델의 역할·입출력을 분리한다. 서로 다른 기반 모델이나 GPU 두 대가 반드시 필요한 것은 아니다.
동아리 서버 사양에 따라 별도 모델, 공통 기반 모델과 역할별 어댑터 등 배포 방식을 나중에 결정한다.

| 구성 | 책임 | 출력 |
| --- | --- | --- |
| 대화 에이전트 LLM | 맥락 이해, 쉬운 질문, 도구 선택, 근거 있는 안내, 접수 내용 정리 | 사용자 메시지와 다음 행동 제안 |
| 분류 LLM | 안내/접수 등 목적, 민원 주제, 법적 유형 후보, 서비스·관할·부서 후보, 부족한 정보 분류 | 스키마를 지키는 JSON과 짧은 근거, 판단 보류 |
| 서버 실행기 | 로그인·소유권·입출력 검증, 도구 실행, 상태·동의·감사 기록 관리 | 실제 허용된 조회·저장·접수 결과 |
| 정책·서비스 DB | 공식 업무분장, 최신 복지·민원 안내, 자료 요구 기준, 원문 출처 | 검색 가능한 버전 자료 |

분류 모델은 **LLM의 문맥 판단**을 사용한다. 키워드 몇 개로 최종 부서를 정하는 방식을 운영
분류기로 사용하지 않는다. 검색에서 단어 검색을 보조적으로 쓰거나 서버에서 ID·권한·기간을
검증하는 것은 분류 판단과 다른 역할이다. 기존 규칙 모드는 오프라인 회귀 테스트와 성능 비교에
남겨두되, LLM 장애 시 이를 몰래 운영 분류로 대체하지 않는다.

분류 입력에는 비식별 대화, 시민이 확인한 위치·상황, 최신 분류표와 부서 후보 근거를 넣는다.
분류 결과의 예시 계약은 다음과 같다. 식별자는 모두 검수된 목록 안에서 선택해야 한다.

```json
{
  "schema_version": "1",
  "taxonomy_version": "검수된 버전 ID",
  "intent": "complaint",
  "issues": [{
    "topic_ids": [],
    "legal_type_candidate": null,
    "service_candidates": [],
    "department_candidates": [],
    "missing_slots": ["incident_location"],
    "evidence_source_ids": [],
    "review_required": true
  }],
  "abstained": true
}
```

`null`·빈 후보·판단 보류를 허용한다. 설명할 수 없는 부서 ID나 없는 서비스를 만들어내면
검증에서 거절하고 재질문·사람 확인으로 전환한다. 모델이 출력한 숫자 confidence를 검증된
정확도처럼 사용하지 않으며, 라벨별 평가와 보류율을 함께 확인한다.

### 에이전트 도구

| 도구 | 용도 | 실행 범위 |
| --- | --- | --- |
| `search_services` | 성남시·경기도·전국 공공서비스 찾기 | 허용된 공개 데이터·검색 DB |
| `get_service_detail` | 지원 내용·신청방법·기한·필요 자료 읽기 | 출처·시행일·갱신일 포함 |
| `classify_request` | 별도 LLM 분류 호출 | 현재 카탈로그로 검증 |
| `find_related_incidents` | 같은 현장 문제 후보 검색·관계 비교 | 권한이 확인된 본인 기록 또는 승인된 사건 색인. 공개 가능한 필드만 대화에 반환 |
| `resolve_jurisdiction` | 위치·시설 관리 주체와 부서 후보 확인 | 확인 가능한 업무분장. 모르면 보류 |
| `request_information` | 누락된 정보나 선택적 사진 요청 | 왜 필요한지 설명, 시민 답변 대기 |
| `prepare_submission` | 구조화된 접수 요약 작성 | 대화 초안에만 저장 |
| `submit_complaint` | 확정한 민원 저장·전송 | 현재 요약에 대한 시민 확인, 권한·필수값 검증 후 실행 |
| `get_my_complaint` | 기존 민원과 후속 진행 조회 | 요청자 소유·조회 권한 검사 |

LLM은 임의 SQL, 임의 URL 호출, 타인 민원 검색 권한을 갖지 않는다. 도구에 접근할 때마다
서버가 검증한다. 조회 자료와 민원 본문에 들어 있는 명령은 에이전트 지시로 실행하지 않는다.
한 차례 응답의 도구 호출 수·시간·재시도 상한을 두고 한도에 도달하면 대화를 반환한다.
검색 실패 시 출처 없는 정책·금액을 생성하지 않는다.

복지의 지원대상·신청방법 안내는 검색 근거로 답할 수 있다. 개별 수급 자격, 처분의 적법성,
허가·과태료·보상 결론은 담당자의 확인 영역으로 둔다. 공무원의 답변 승인과 민원 종결도
모델이 대신 결정하지 않는다.

## 5. 챗봇 UI와 서버 연결 자리

### 첫 UI 작업 범위

- 시민 메인의 주 행동을 “민원·생활정보 물어보기”로 두고 기존 민원 작성 진입을 대화로 연결.
- 큰 입력창에 “불편한 점이나 궁금한 일을 편하게 적어 주세요” 안내. 부서 선택은 시작 조건에서 제외.
- “생활불편 알려주기”, “복지혜택 알아보기”, “내 민원 확인”은 선택 가능한 시작 예시로 제공.
- 메시지, 선택 답변, 출처 카드, 추가정보 요청, 사진 상태, 접수 요약, 접수 결과를 별도 UI로 구성.
- 입력 중, 자료 검색 중, 추가 답변 대기, 모델 연결 실패, 재시도 상태를 명확히 표시.
- 모바일에서는 한 열로 구성하고 입력창과 현재 질문을 쉽게 찾게 한다.
- 긴 설명은 쉬운 요약을 먼저 보여주고 상세 근거를 펼쳐 보도록 한다.
- 키보드 조작·초점 유지·화면낭독기 안내·확대 보기를 검증한다. 버튼 높이는 48px 이상을 설계 목표로
  두고 색만으로 상태를 전달하지 않는다. 메시지 스트리밍을 글자마다 낭독하지 않게 한다.
- 음성 입력·읽어주기는 후속 기능 자리로 설계한다. 아직 작동하지 않는 기능은 준비 중임을 표시한다.
- 대화가 어려운 사람에게 간단 입력 방식과 공식 전화·방문 안내로 이동할 수 있는 경로를 제공한다.

대화 예시와 접근성 문구는 합성 데이터로 먼저 검증한다. 모델 미연결 상태의 UI는 **시연 모드**임을
표시하며, 미리 정한 시나리오 재생을 실제 LLM 추론으로 소개하지 않는다.

### 교체 가능한 연결 계약 — 대화·도구 시연 인터페이스 구현

v1 `ChatAgentProvider`와 v2 `AgentPlanner`, 엄격한 JSON, 서버 소유 초안·최종 확인 API를
구현했다. v2는 검수한 로컬 자료 검색과 필요 정보 조회를 실행한다. 사진 선택·접수·조회는
모델과 독립적으로 구현했고 실제 추론·외부 검색·사진 판독·정부 연결은 후속 작업이다.
현재 설정은 `CHAT_PROVIDER=agent_demo|demo|club|unavailable`이고
기본값은 `agent_demo`다. `club`의 현재 설정은 [전용 서버 계약](CLUB_MODEL_SERVER.md)을 따른다.

| 연결부 | 준비할 인터페이스 | 나중에 받을 정보 |
| --- | --- | --- |
| 대화 모델 | v2 `AgentPlanner`: 메시지·도구 결과 입력, 엄격한 행동 JSON 출력 | 서버 주소, 모델 ID, 인증, 스트리밍·도구 호출 방식 |
| 분류 모델 | `ClassifierProvider`: 비식별 입력, 버전 분류표, 구조화 JSON | 분류 모델 ID, 입력 길이, 출력 스키마, 시간제한 |
| 검색 | `ServiceRepository` / `KnowledgeRetriever` | 임베딩 모델, 색인 저장소, 배치 갱신 방식 |
| 중복·사건 연결 | `IncidentMatcher`: 후보 검색과 분류 LLM 관계 비교 | 사건별 시간·위치 기준, 색인 접근 정책, 담당자 연결 검토 |
| 사진 | 현재 `citizen_photos`의 접수·검사·비공개 조회 / 후속 `VisionProvider` | 운영 저장소·보존 정책, OCR·사진 속 식별정보 처리 방식 |
| 정부 접수 | `GovernmentSubmissionAdapter` | 기관 승인, 테스트 환경, 접수·조회·첨부·통지 명세 |

대화 연결에는 `CHAT_ENDPOINT_URL`, `CHAT_MODEL_ID`, `CHAT_API_KEY`를 사용한다.
후속 설정 후보는 `CLASSIFIER_PROVIDER`, `CLASSIFIER_BASE_URL`, `CLASSIFIER_MODEL_ID`,
`GOV_SUBMISSION_MODE`다. 인증키는 서버의
비밀값 설정으로 받고 브라우저·Git·일반 로그에 넣지 않는다. 현재의 `AI_PROVIDER` 설정과는
마이그레이션 방침을 정한 뒤 연결한다.

서버 계약은 대화 세션·메시지, 부족한 정보, 출처, 접수 초안 버전, 첨부 ID, 확인·중복 방지 키를
포함한다. 한 HTTP 규격으로 두 모델을 감싸는 내부 게이트웨이를 두면 UI가 추론 엔진 종류에
직접 의존하지 않는다. 요청 취소, 시간초과, 오류 메시지, 모델 버전도 계약에 포함한다.

## 6. 데이터 수집과 학습 계획

**공식 CSV·API → 공식 HTML → 첨부 서식·PDF/HWP/HWPX** 순으로 수집한다. 우선 자료는
성남시 민원 편람·업무분장·서비스 목록과 복지로·공공서비스 API다. 시민 민원 게시판을 무작정
긁어 학습 데이터로 쓰는 방식은 기본 계획에서 제외한다.

1. 출처 목록과 이용 조건을 기록한다. 조회·가공·재배포·모델 학습 가능 여부를 각각 확인한다.
2. 허용된 문서·페이지를 낮은 요청 빈도로 수집하고 페이지 수·실행시간·파일 크기에 상한을 둔다.
3. 원문 주소, 문서 ID, 게시·갱신·시행일, 해시, 수집 시각, 라이선스와 파서 버전을 저장한다.
4. 목록만으로 부서를 결정하지 않고 상세 페이지·서식의 요건·담당 과까지 연결한다.
5. 같은 업무의 과거 공고·구 버전·중복을 묶고, 최신 여부와 적용 지역을 검수한다.
6. 공식 분류를 원본 이름·ID로 보관하고 프로젝트 내부 분류와 연결하는 대응표를 만든다.
7. 검수한 자료만 검색 DB에 게시하고, 변경 감지 후 재검수·교체·철회할 수 있게 한다.

크롤러는 공식 공개 경로와 허용된 다운로드를 대상으로 한다. robots.txt와 이용 조건을 확인하고,
로그인·CAPTCHA·비공개 페이지를 우회하거나 화면용 내부 통신 주소를 공개 API로 취급하지 않는다.
초기 수집은 한 번 실행하고 종료하는 작업으로 만들며 완료·실패·중단 기록을 남긴다.

**검색 자료와 파인튜닝 자료는 분리한다.** 복지 금액·기간·담당 부서처럼 바뀌는 사실은 최신
DB에서 찾는다. 파인튜닝은 질문 방식, 분류, 정보 추출, 도구 선택, 판단 보류 행동을 개선한다.
기존 데모 민원 기록은 학습에 재사용하지 않고 허용된 별도 학습 코퍼스를 만든다.

초기에는 실제로 검수 가능한 10~15개 업무를 시연 범위로 선정한다. 각 업무에 일상 표현,
오타, 장문, 위치 누락, 두 가지 문제의 혼합, 범위 밖 요청을 포함하는 예시를 구축한다.
원문 민원과 첨부사진 확보가 필요한 단계는 별도 제공·비식별·사용 권한을 먼저 정한다.

데이터 라벨은 분야·법적 유형 후보·서비스·관할·부서·필요 정보·보류 사유를 포함한다. 애매한
사례는 두 사람이 검토하고 의견 불일치를 남긴다. 동일 사건·문장 변형·생성 템플릿은 학습과
평가 세트에 나뉘어 들어가지 않도록 묶어서 분리한다.

동아리 서버의 GPU·VRAM·메모리·동시 사용자 목표가 확인된 뒤 기반 모델과 학습 방식을 결정한다.
우선 기본 모델 + 검색 + 구조화 출력 기준선을 평가하고, 파인튜닝 후 같은 고정 평가셋으로
비교한다. 실행 이름은 대화·분류·학습을 구분하고 실행 담당자, 종료 조건, 최대 학습 step,
중단 방법을 기록해 GPU 작업이 방치되지 않도록 한다.

## 7. 공무원 업무 부담과 병목 조사

현재 확인된 지역 근거는 바로문자의 부서 답변·소통관 재확인·사후관리와, 시의회의 답변 완료와
실제 조치 구분 논의다. 전국 자료에는 기관 추천과 AI 답변 지원을 통한 업무 개선 추진이 있다.
이를 성남시의 실제 시간 절감 수치로 바꾸어 주장하지 않는다.
[바로문자 운영](https://snvision.seongnam.go.kr/22943),
[성남시의회 회의록](https://sncouncil.go.kr/record/recordView.do?key=cbf9a745fc3f512950d381c8c52264691e7db7852a029c82ade24fe8248accc1d6b8d99955bafe2b)

| 확인할 병목 가설 | 관찰·인터뷰 항목 | 에이전트가 줄이려는 일 |

| 잘못된 소관 배정과 이송 | 최초 담당 판단 방법, 재배정 횟수, 소관 이견, 인계 대기 | 업무분장·관할 근거가 있는 후보 제시 |
| 위치·시점·자료 누락 | 보완 연락 횟수, 자주 빠지는 정보, 회신 대기시간 | 시민 대화 중 필요한 정보 수집 |

접수·콜센터, 생활민원 처리 부서, 복지 안내, 검토·총괄 담당자를 합쳐 4~6명 인터뷰하는 것을
목표로 한다. 실제 사건을 복사하기보다 익명화된 업무 예시나 빈 양식으로 절차를 재구성한다.
인터뷰가 확보되지 않으면 공개 자료 기반 가설로 표시하고, 확정된 내부 프로세스라고 소개하지 않는다.

시민 사용성 검증은 디지털 사용에 익숙하지 않은 참여자를 포함해 5~8명부터 시작한다.
기존 사이트와 시제품에서 같은 합성 과제를 수행하게 하고 성공률, 소요시간, 도움 요청, 이탈,
추가 질문 횟수를 비교한다. 정보 안내 정확도·접수 누락·직원 재작업량도 함께 본다.

## 8. 4명 역할 분담

아래 배분은 제안이며 개인 이름과 실제 역량에 맞춰 조정한다. 각 영역에 책임자 한 명과
검토자 한 명을 둔다.

| 역할 | 책임 작업 | 구체적 산출물 | 검토자 |
| --- | --- | --- | --- |
| A: 기획·업무·데이터 검수 — 사용자에게 제안 | 시연 범위, 시민·공무원 인터뷰, 실제 절차·부서 매핑 검수, 일정·발표 | 업무 10~15개 목록, 인터뷰 노트, 확정 분류·부서 대응표, 평가 과제 | D |
| B: 시민 UI·접근성 | 대화 화면, 선택·사진·요약·접수 결과, 모바일·키보드·낭독기 검증 | 모델 없이도 동작을 검토할 수 있는 시연 UI, 컴포넌트·사용성 결과 | A |
| C: 서버·데이터 수집·연계 | 수집기, 정책 DB, 세션·접수·첨부·감사, 조회 API 및 모델 어댑터 | 출처 레지스트리, 검수 대기 데이터, API 계약, 접수·조회 서버 | B |
| D: 모델·학습·평가 | 대화 모델·분류 LLM, 데이터 라벨링 지침, 파인튜닝·서빙 | 학습 데이터 버전, 모델 2종 인터페이스, 고정 평가셋·성능 보고서 | C |

사용자가 먼저 준비해 주면 진행이 빨라지는 것은 다음과 같다.

1. 네 명의 이름·강점과 역할 확정, 공모전 마감일·시연 시간·제출 형식 공유.
2. 시연할 업무 10~15개 선정. 생활불편과 복지 안내를 함께 포함하되 과도하게 넓히지 않기.
3. 공무원·콜센터 또는 관련 실무자 인터뷰 연결, 디지털 취약 사용자 테스트 참여자 섭외.
4. 공공데이터포털 활용신청 담당자 지정. 키는 담당 개발자의 서버 비밀값으로 설정하고 채팅에 붙이지 않기.
5. 추후 동아리 서버의 GPU 종류·VRAM·개수, RAM, 운영체제, 외부 접속 방식, 담당자, 이용 가능 시간 공유.
6. 확보 가능한 공식 업무분장·민원 분류표·서식의 출처와 사용 범위 공유.

API와 서버 정보가 없어도 B는 UI, A는 업무·사용성 검증, C는 데이터 스키마·시연 접수,
D는 분류 계약과 평가셋을 먼저 진행할 수 있다.

## 9. 단계별 계획과 완료 기준

기간은 일정 협의를 위한 4주 예시다. 마감·참여시간·서버 준비일에 맞춰 조정한다.

| 단계 | 작업 | 완료 기준 |
| --- | --- | --- |
| 지금 | 이 계획, 실제 페이지 분석, 분류·출처 초안 | 현재 구현·확인 사실·미확인 사항 구분 |
| 1주차 | 역할·업무 범위 확정, 출처 레지스트리, 대화 UI와 두 모델 계약 | 10~15개 대표 업무와 합성 대화 시나리오, 검수 가능한 UI |
| 2주차 | 공식 자료 수집·검수, 복지 조회, 대화 세션·추가 질문·접수 요약 연결 | 출처 안내 및 시민 확인 후 데모 접수·본인 조회가 한 흐름으로 동작 |
| 3주차 | 동아리 모델 연결, LLM 분류, 도구 호출, 사진 처리 범위 구현 | 모델 오류·보류·질문·혼합 요청·재시도까지 검증 |
| 4주차 | 파인튜닝 전후 비교, 시민·직원 평가, 발표 자료 | 정확도와 사용성 결과, 접수·조치 구분, 한계와 연계 계획을 근거로 설명 |
| 기관 협의 이후 | 정식 본인확인·정부 접수·진행 조회 연계 | 승인된 테스트 환경에서 수신·접수번호·첨부·권한·중복 방지 검증 |

평가에서는 분류 Macro-F1·상위 후보 적중률·보류율·잘못된 부서 추천을 함께 본다. 대화는
불필요한 재질문, 정보 누락, 범위 밖 응답, 잘못된 도구 선택을 측정한다. 정책 안내는 출처
정확성·기준일·지역 적합성과 근거 없는 금액·자격 단정을 평가한다.

필수 통과 항목은 미확인 공식 접수 완료 표시 0건, 중복 접수 0건, 타인 민원 접근 0건,
존재하지 않는 분류·부서 ID 수락 0건, 미승인 외부 전송 0건이다. 이는 목표·시험 기준이며
현재 달성한 서비스 성능 수치가 아니다.

## 10. 다음 구현의 경계

구현한 범위는 대화 UI·비공개 초안·시민 확인 후 접수, 공식 자료용 JSON·본문 추출기·검수
등록/승인/철회, 읽기 도구 실행기와 출처 카드, 선택적 사진 접수·조회다. [시민 HTTP 계약](CHAT_API.md),
[도구 JSON v2](AGENT_API.md), [데이터 수집·검수 절차](SERVICE_DATA_PIPELINE.md)를 기준으로 연결한다.

다음 우선순위는 조사 후보 12개의 최신 원문·이용 조건 검수와 생활불편·복지 혜택 확장,
동아리 대화 모델의 실제 연결·평가와 별도 LLM 분류기 어댑터, 동적
추가 질문과 사진 속 식별정보 검토·AI 판독이다. AI 서버 준비 중에는 본인 민원 추가 문의와
시민 사용성·접근성 개선을 진행할 수 있다. 실제 HTML 선택자·이용 조건 확인 전에는 네트워크 수집을 활성화하지
않으며, 합성 업무 3개와 미확인 사항이 남은 조사 후보를 구분한다. 기관 접수와 의미상 중복
사건 연결, 음성·스트리밍은 별도 단계다. 기존 시민 조회·명시적 답변 공개·감사 기능은 재사용한다.
