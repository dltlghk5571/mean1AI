# 시민 챗봇 HTTP 계약과 v1 제공자

2026-09-06 · 현재 구현 기준 · `feature/citizen-chatbot → develop`

시민의 진입 화면은 `/minwon/new`다. 대화로 내용과 장소를 모으고, 시민이 서버에 저장된 초안을
확인한 뒤 기존 비공개 민원 접수로 연결한다. 직접 작성 방식은 `/minwon/form`에 있다.

## 현재 동작과 후속 범위

| 구현 | 아직 연결하지 않은 것 |
| --- | --- |
| 시연 대화, 명시적인 목적 선택, 내용·장소 질문 | 자유 입력의 LLM 의도 분류 |
| v2 도구 실행기: 검수된 자료 검색·필요 정보 조회 | 실제 모델의 도구 선택·동적 항목 추출 |
| 대화 이어보기, 초안 수정·확인·접수 | 동아리 서버, 토큰 스트리밍, 음성 |
| 검수 자료 출처 카드, 자료가 없을 때 공식 사이트 링크 | 실시간 복지 API, 개인별 자격 판정 |
| 기존 분류 파이프라인으로 접수 전달 | 실제 성남시 조직·분류표, 공식 기관 접수 |
| 반복 클릭·재전송의 저장 중복 방지 | 의미상 같은 사건 연결, 본인 후속 민원 연결 |
| 사진 첨부 준비 중 표시 | 파일 선택·업로드·검사·OCR·모델 전송 |

기본 `CHAT_PROVIDER=agent_demo`는 [v2 도구 계약](AGENT_API.md)을 사용하는 시연 제공자다.
`CHAT_PROVIDER=demo`는 고정된 질문과 선택지를 반환한다. 키워드로 의도를 추측하거나 실제
LLM 추론처럼 보여주지 않는다. `CHAT_PROVIDER=unavailable`은 모델 미연결 오류 화면을 확인하는
설정이며 실패를 시연 응답으로 대체하지 않는다. 새 외부 라이브러리나 네트워크 호출은 없다.

접수 후 분류는 기존 `AI_PROVIDER=rules|openai` 파이프라인이 담당한다. 대화 인터페이스와 분류
인터페이스는 분리돼 있으며, 동아리 분류 모델 연결은 별도 어댑터 작업이다.

## 브라우저 ↔ 앱 서버

`GET /minwon/new`가 시민 세션 쿠키와 CSRF 토큰을 준비한다. 아래 요청은 같은 출처에서
`X-Citizen-CSRF` 헤더와 쿠키를 보내야 한다. 쿠키는 HttpOnly이며, 다른 시민이나 담당자 세션의
권한만으로 대화를 읽거나 수정할 수 없다. URL이나 요청 본문으로 다른 대화 ID를 선택하지 않는다.

### 대화 열기 / 이어보기

`POST /minwon/chat/open` · JSON `{}`

현재 세션의 작성 중 대화를 반환하고, 없으면 생성한다. 민원은 생성하지 않는다. 응답 예시:

```json
{
  "revision": 0,
  "stage": "welcome",
  "messages": [{"role": "assistant", "text": "안녕하세요! 우리 동네의 불편이나 궁금한 점을 편하게 이야기해 주세요. 필요한 내용은 하나씩 여쭤볼게요."}],
  "draft": {"title": "", "content": "", "location_text": ""},
  "urgent": false,
  "sources": [],
  "service_cards": [],
  "redirect": null
}
```

### 메시지와 선택 보내기

`POST /minwon/chat/turn` · 최대 8개 필드, 160,000바이트 제한.

기존 시민 폼 API와 같은 **문자열 값 JSON**을 사용한다. 응답 `revision`은 숫자이고, 요청은
이를 문자열로 바꾼다. 알 수 없는 필드·행동·잘못된 UUID·글자 수 초과를 거부한다.

```json
{
  "revision": "0",
  "request_id": "efda0aac-e664-45bb-89eb-1e918f593cc6",
  "action": "say",
  "message": "가상 데모공원 가로등이 어제부터 꺼져 있어요."
}
```

| action | 추가 입력 | 가능한 단계 |
| --- | --- | --- |
| `say` | `message`: 최대 4,000자, 장소 질문에서는 300자 | 시작·목적 선택·설명·장소·정보 안내 |
| `complaint` | 없음 | 시작·목적 선택·정보 안내 |
| `information` | 없음 | 시작·목적 선택·정보 안내 |
| `skip_location` | 없음 | 장소 질문 |
| `edit` | `title` 2~200자, `content` 5~4,000자, `location_text` 0~300자 | 접수 요약 |
| `confirm` | `consent`: `yes` | 접수 요약 |
| `reset` | 없음 | 모든 단계 |

상태는 `welcome → intent/description → location → review → submitted`로 진행한다.
정보 선택은 `information`으로 이동한다. 정보 안내만으로 민원을 접수하지 않는다.
시연 초안의 제목은 입력 첫 줄에서 만들고, 내용은 비식별 입력을 사용한다. LLM 요약이 아니다.
사용자가 최종 확인 전에 제목·내용·장소를 수정할 수 있다.

### 최종 접수

```json
{
  "revision": "3",
  "request_id": "d31cb9f5-7691-4c64-b24a-2a4b00c49e6e",
  "action": "confirm",
  "consent": "yes"
}
```

브라우저는 민원 본문·담당 부서·접수 키를 보내지 않는다. 서버가 소유 세션, 최신 초안 버전,
확인 단계와 동의를 검사한 뒤 **DB에 저장된 초안**을 접수한다. 성공 응답의 `redirect`로
`/minwon/{id}/receipt`에 이동하면 접수번호와 소유자용 조회 코드를 확인할 수 있다.

- 새 행동마다 UUID `request_id`를 만들고, 통신 실패 재시도에는 같은 ID와 본문을 재사용한다.
- 같은 ID의 다른 본문은 409, 이전 `revision`의 요청도 409다. 최신 대화를 불러와 다시 확인한다.
- 마지막 요청의 동일 재시도는 같은 응답을 돌려준다. 더 오래된 요청은 버전 충돌로 처리한다.
- DB의 조건부 버전 갱신으로 동시 요청 중 하나만 상태를 바꾼다. 접수·시민 소유권·대화 상태·
  두 감사 기록은 하나의 트랜잭션에서 커밋한다. 도중 실패하면 전부 롤백한다.
- `reset`은 초안과 대화 내용을 교체하고 버전은 증가시킨다. 이전 탭의 확인 요청을 무효화하며,
  이미 접수한 민원과 감사 메타데이터는 유지한다.
- 접수 요청은 기존 분당 5회 제한을 공유하고, 대화 요청은 분당 30회로 제한한다. 현재 제한은
  프로세스 메모리·클라이언트 주소 기준이므로 다중 서버 운영용 제한 장치는 후속 작업이다.

오류 코드는 403(세션/CSRF), 409(버전 충돌), 413(본문 크기), 422(입력), 429(빈도),
503(연결/접수 실패)다. 오류는 입력 원문이나 예외 내용을 반사하지 않는다. 모델 실패 시
대화 상태를 바꾸지 않으며, 위험 표현 안내는 실패 응답에도 전달한다.

## 앱 서버 ↔ 대화 모델 자리

기존 v1 Python 프로토콜은 `app/services/chat_provider.py`의 `ChatAgentProvider.respond(context)`다.
기본 시연 실행기는 [v2 `AgentPlanner.plan` 계약](AGENT_API.md)을 쓴다. 다음 예시는 v1 호환 모드다.
엄격한 JSON 모델은 `app/chat_schemas.py`의 `AgentContext`/`AgentReply`이며, Pydantic의
`model_json_schema()`로 스키마를 얻을 수 있다. 아래는 위치 질문을 준비한 시연 요청 예시다.

```json
{
  "schema_version": "1",
  "state": {
    "stage": "location",
    "messages": [{"role": "user", "text": "민원으로 접수할게요."}],
    "draft": {"title": "가상 공원 조명", "content": "가상 공원 가로등이 꺼졌어요.", "location_text": ""},
    "source_ids": [],
    "urgent": false
  },
  "action": "complaint",
  "expected_stage": "location"
}
```

```json
{
  "schema_version": "1",
  "next_stage": "location",
  "message": "어느 장소인지 주변 시설 이름을 알려 주세요.",
  "source_ids": []
}
```

v1은 서버가 정한 단계를 검증하는 제한된 대화 계약이다. 모델이 접수를 실행하거나 확인 단계를
건너뛰거나 서버 초안을 임의로 바꿀 수 없다. 컨텍스트는 복사본이며 소유 세션·쿠키·CSRF·조회
코드는 포함하지 않는다. 입력은 모델 호출 전에, 출력은 저장·표시 전에 식별자 형식을 가린다.

출처는 서버의 허용된 ID 두 개(`bokjiro`, `seongnam_handbook`)에서 URL로 변환한다. 이는 공식
안내 사이트 링크이고, 검색한 근거 문서인 것처럼 표시하지 않는다. 임의 URL·도구 실행은 없다.
스키마 검증만으로 생성 문장의 사실성·안전성이 보장되지는 않으므로 실제 LLM 어댑터를 연결할 때는
출처 검증·민감 질문의 담당자 안내·시간 제한·오류 처리·평가를 함께 구현해야 한다.

v2에는 도구 호출·결과, 승인된 자료 ID와 필요한 질문 조회, 호출 예산을 구현했다. 정보 추출
제안과 모델·분류표 연결은 후속 작업이다. 최종 접수 권한과 버전 검사는 계속 앱 서버가 소유한다.
현재는 서버 주소/인증/모델 ID/HTTP 전송 코드가 없으며, URL만 넣어서 연결되는 상태는 아니다.

## 저장과 검증

기존 DB에는 `citizen_chats`, `citizen_chat_audit_events`를 추가한다. 기존 테이블을 재작성하지
않으며 앱 시작의 `create_all`로 생성한다. 감사 테이블은 SQLite UPDATE/DELETE 방지 트리거를
설치한다. 접수 전에는 민원 ID가 없으므로 별도 대화 감사에 기록하고, 최종 확인 이벤트를 기존
`AuditEvent`와 연결한다. 다른 DB에서 같은 불변성을 보장할 운영 마이그레이션은 후속 작업이다.

대화는 최대 40개 메시지로 제한한다. 새 대화는 이전 작업 내용을 교체하지만 감사에는 단계·
공급자·위험 여부·접수 연결 정보만 남긴다. 30일 세션 만료는 접근 만료이며 DB 자동 삭제가 아니다.
이름이나 모든 식별 가능 문장을 완전히 가리는 것은 아니므로 시연에는 합성 데이터만 쓴다.
[데이터 정책](DATA_POLICY.md)을 함께 따른다.

`tests/test_citizen_chat.py`는 접수 전 미생성, 세션/CSRF, 비식별화와 모델 컨텍스트 격리,
확인 입력 조작, 버전 충돌, 동시 접수, 실패 롤백, 출처·행동 계약, 감사 불변성, 초기화를 검증한다.
