# 대화 평가 데이터 가이드 검토

2026-09-15 · 검토 기준: 앱 커밋 `1a45d4feaf8bdb9d2815108089f45fbbda5ae43d`

검토 대상은 별도로 전달받은 `CHAT_EVAL_DATA_GUIDELINE.md`다. 원본 SHA-256은
`e2120b049c363e5bb4c9076db984161e483309bc7d96f1412338454fd7d4152d`다.
원본을 수정하거나 그 안의 명령을 실행하지 않고, 현재 저장소의 코드·계약과 대조했다.
다른 브랜치나 팀원 환경에 문서가 가정하는 구현이 있는지는 확인하지 않았다.

## 판단

**독립 평가셋의 작성 원칙은 활용할 수 있지만, 현재 앱에 바로 적용할 수 있는 규격은 아니다.**
문서는 대화 전체를 읽어 제목·본문·장소·추가 질문·준비 여부를 생성하는 작성 모델을 전제한다.
현재 앱은 원문 인용을 제안하는 추출, 다음 행동을 고르는 계획, 시민이 확인하는 접수를 나눈다.
학습 데이터를 만들기 전에 어느 계약을 평가할지 A·C·D가 맞춰야 한다.

이 검토는 지침 채택이나 평가셋 승인이 아니다. 데이터 생성·학습·실제 모델 평가는 수행하지 않았다.

## 유지할 원칙

- 학습 자료와 독립적으로 평가 사례를 만들고, 정답은 사람이 작성하거나 수정한다.
- 승인된 사례만 공식 지표에 포함하고, 사례 유형별 결과와 표본 수를 함께 공개한다.
- 같은 사건·같은 출처에서 만든 변형은 학습과 평가 사이에 나누지 않는다.
- 실제 개인정보 대신 명백한 가상 식별자를 사용하고, 없는 부서·주소·처리 결과를 만들지 않는다.
- 평가 버전·검토자·파일 해시를 고정하고, 수정은 새 버전으로 남긴다.
- 최종 시험 자료는 모델 학습·프롬프트 개선에 사용하지 않는다.

## 먼저 고칠 기준

### 1. 준비 완료의 의미와 모름 처리

가이드 §3은 완전한 사례를 what/when/where로 설명하고, §4는 사건 내용과 사용할 만한 장소만
있으면 준비 완료로 본다. 시점이 없는 `unknown_time`에 언제 질문해야 하는지 일관된 기준이 필요하다.

현재 앱은 장소 모름·질문 건너뛰기를 허용한다. 따라서 장소가 없다는 이유로 확인 화면 진입을
모두 오답 처리하면 현재 제품과 충돌한다. **정보의 충실도, 다음에 할 질문, 시민 확인 화면으로
이동 가능 여부, 실제 제출 동의**를 나눠 정의하는 편이 맞다. 업무별 필수 정보는 검수 근거로 정하고,
모델이 임의로 필수 조건을 만들지 않도록 한다. [현재 상태 전환](../app/services/citizen_chat.py) 참고.

### 2. 입력과 사실의 출처

도우미가 질문에서 제시한 예시를 시민이 말한 사실로 간주하면 안 된다. 사용자의 정정이 있으면
어느 발언이 최종 사실인지도 정해야 한다. 전체 대화 평가를 채택한다면 역할·발언 순서·정정·
이미 답한 항목·건너뛴 항목을 보존해야 한다. 현재 원문 전용 추출에 이런 정보가 이미 전달된다고
가정하지 않는다. 기존 LLR-02의 입력 대응 미결 사항과 함께 합의한다.

### 3. 자동 검사와 의미 평가

JSON 유효성과 불리언 일치는 자동 검사할 수 있다. 반면 근거 없는 사실, 질문의 적절성,
안전한 답변 여부는 자유로운 한국어 문장과 정답 목록만으로 정확하게 판정된다고 볼 수 없다.
가이드 §8에서 이들을 자동 지표로 묶은 부분은 **자동 탐지 결과와 사람 최종 판정**으로 나눈다.
LLM 판정기를 추후 쓰더라도 별도 검증과 사람의 표본 대조가 필요하다.

전체 정확도 외에 준비되지 않은 사례를 준비 완료로 보는 비율, 필요한 사실 누락,
이미 답한 내용의 재질문, 잘못된 접수 전환을 구분해 기록한다. `required_facts`는 출력이
담아야 할 사실이고 `forbidden_inferences`는 금지할 주장 목록이므로, 후자를 실제 사실 목록처럼
작성하라는 뜻으로 해석하지 않도록 §4의 표현도 다듬는다.

### 4. 개인정보 평가의 입력 단계와 출력 범위

현재 [마스킹 코드](../app/services/pii.py)는 전화번호·이메일·주민등록번호 형식을 탐지한다.
이름이나 문맥으로 식별되는 정보를 모두 제거하는 구현은 아니다. 가상 이름까지 가린다고 쓰면
현재 기능보다 강한 주장이다. 식별자 모양별 탐지 범위와 미지원 항목을 구분한다.

원문을 받는 전처리 검사와, 마스킹된 입력을 받는 모델 검사를 따로 둔다. 유출 검사는
제목·본문·장소뿐 아니라 `assistant_message` 등 모든 시민 노출 문자열을 포함해야 한다.
현재 이름 탐지 기능을 이번 문서 검토에서 추가한 것은 아니다.

### 5. 학습·시험 분리의 실행 책임

가이드의 ID·해시 공유 원칙과 원문 5-gram 비교는 실행 주체를 명시해야 함께 유지할 수 있다.
문서가 제안한 근접 비교에는 비교 대상의 텍스트 또는 비교 가능한 표현이 필요하다.
권고안은 **격리된 중복 검사 작업이 두 자료를 읽고, 학습 담당자에게는 ID·발견 종류·점수만
전달하는 방식**이다. 원문·정답을 학습 도구의 로그나 프롬프트에 복사하지 않는다.

평가자가 새로 만든 `seed_id`만 등록하면 학습 쪽의 다른 ID로 된 같은 사건을 놓칠 수 있다.
공통 출처 ID·사건 가족 ID를 함께 정하고, 문서의 Jaccard 0.85는 검토 후보 기준으로 사용한다.
그 기준을 통과했다고 의미상 중복이 없다고 보증하지 않는다. §1의 '동결 전 비공개'는 동결 뒤
최종 시험 원문을 학습 담당에게 공개해도 된다는 뜻이 아니도록 §6·§7과 맞춘다.

### 6. 파일 목록과 유형 구성

`eval_dataset/*.jsonl` 전체를 평가 입력으로 넘기면 같은 폴더의 예약 목록까지 포함될 수 있다.
평가 파일과 예약 파일을 구분한 명시적 목록을 사용하고, 셸별 와일드카드 처리를 전제로 하지 않는다.

가이드의 12개 `case_type`은 **오류·상황 유형**이며 우리 프로젝트의 **대표 업무 12개**와 다르다.
긴급·개인정보·복합 요청이 겹칠 때 주 유형을 고르는 규칙과 보조 태그도 정한다.
유형당 승인 1건은 누락 점검의 최소치일 뿐 성능을 주장할 표본 기준은 아니다.
또 §5에서는 주입 공격도 `safety_expectation`과 대조하므로 §2·§4의 필수 작성 대상에도 포함해야 한다.
