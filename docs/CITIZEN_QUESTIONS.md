# 상황별 추가 질문과 모델 연결 경계

2026-09-12 갱신 · `feature/citizen-chatbot → develop`

`/minwon/new`의 **어떻게 말할지 막막하다면, 상황부터 골라 보세요**에서 생활불편 8개,
복지 안내 4개를 선택할 수 있다. 선택은 필수가 아니며, 자유 입력 → 접수 의사 → 내용·장소 →
최종 확인 경로도 유지한다. 서버가 준비되지 않은 기본 시연 모드에서 전 과정을 실행할 수 있다.

## 지금 구현한 동작

- 내용과 장소는 기존 초안을 재사용한다. 장소를 건너뛴 사실도 기억한다.
- 상황마다 추가 질문 2개를 한 번에 하나씩 묻는다. 답변, 모름·건너뛰기, 처음 내용에 이미
  설명함, 추가 질문 끝내기를 지원한다. 선택적 [추출 제안·시민 확인](CHAT_EXTRACTION.md)으로
  처음 쓴 글에서 확인한 답변은 다시 묻지 않는다. 실제 추론 모델은 아직 미연결이다.
- 새로고침하면 질문과 답변을 이어간다. 같은 상황을 다시 선택하면 답변을 보존하고,
  다른 상황을 선택하면 추가 답변만 초기화한다. 새 대화는 모든 초안을 초기화한다.
- 확인 화면에서 본문과 개별 추가 답변을 수정한다. 답변은 본문 뒤에 항목명과 함께 붙이며,
  화면의 `submission_content`와 실제 접수 본문이 같다. 건너뜀·본문에 설명함은 새 사실로
  접수 본문에 추가하지 않는다. 답변 500자, 본문과 답변 합계 4,000자 제한을 넘으면 저장을
  거부하고 기존 초안과 입력을 유지한다. 내용을 임의로 잘라서 저장하지 않는다.
- 복지 상황 선택은 안내로 끝난다. **민원으로 접수할게요**와 마지막 동의가 있어야 저장한다.
  복지 상황에서 접수한 민원은 분류 결과와 무관하게 사람 검토를 요구한다. 감사 기록에 남긴
  복지 맥락은 재분류 때도 유지한다.
- 위험 질문은 뜻이 분명한 문장 선택지 또는 건너뛰기로 답한다. “네”만 입력하면 재확인한다.
  위험하다는 답변은 그대로 접수 본문에 포함한다. 질문 문구를 긴급 탐지기에 넣지 않는다.
  위험이 감지되면 아직 묻지 않은 질문을 생략하고 긴급 안내를 먼저 표시한다. 긴급 복지
  안내에는 모델 응답을 기다리지 않는다. 이 화면은 실제 신고·상담을 전달하지 않는다.
- 사진은 최종 확인 화면에서 최대 3장을 선택한다. 사진 준비 여부를 답해도 사진을 요구하거나
  자동 업로드하지 않는다. 사진 없이도 접수할 수 있다.

## 자료 경계

`app/data/citizen_question_templates.json`은 앱에서 작성한 **대화 문구** 12묶음·24항목이다.
앞서 정리한 44개 질문안 중 공통 내용·장소 20항목은 기존 입력을 재사용하고, 나머지 질문을
시민에게 읽기 쉬운 문장으로 다듬었다. 긴급복지에서는 도움의 시점을 먼저 묻는다.

공식 카탈로그의 서비스 ID·부서·자격·금액·법정 필수 서류와 독립적이다. 이 파일은
`seongnam_pilot_candidates.json`을 승인하거나 시민 검색에 공개하지 않는다. 공식 자료의
이용 조건·부서 불일치·관할 미확정 상태와 합성 부서 배정은 그대로다.

## HTTP 계약

기존 [시민 API](CHAT_API.md)의 동일 세션·CSRF·문자열 JSON·revision·request_id 검사를 사용한다.
외부 입력으로 질문 문구, 임의 항목, 답변 사전, 전체 대화 상태를 덮어쓸 수 없다.

| action | 추가 문자열 필드 | 허용 시점 |
| --- | --- | --- |
| `choose_topic` | `template_id` | 시작·목적·설명·장소·확인·안내 |
| `answer_question` | `field_id`, `message` (1~500자) | 현재 추가 질문 |
| `skip_question` | `field_id` | 현재 추가 질문 |
| `already_described` | `field_id` | 현재 추가 질문 |
| `finish_questions` | 없음 | 추가 질문 |
| `revise_question` | `field_id` | 확인·안내 |

예를 들어 `lighting` 선택 후 내용과 장소가 확보되면 `questions` 단계가 된다.

```json
{
  "revision": "4",
  "request_id": "10f50915-4bad-4921-9a0d-370d455c91b2",
  "action": "answer_question",
  "field_id": "observed_time",
  "message": "지난주 저녁부터 그랬어요."
}
```

응답은 기존 필드 외에 `topic_options`, `intake`, `current_question`, `location_checked`,
`submission_content`를 포함한다. `intake.template`은 선택 시점의 문구·버전 스냅샷이며,
`intake.answers`는 항목별 `status`와 비식별 `value`다. 상태는 `answered`, `skipped`,
`in_description`, `not_asked`(위험 안내를 우선해 생략)다. `editing_field`로 수정할 항목을
가리킨다. 새 필드가 없던 기존 대화도 기본값으로 읽는다.

요청 재시도는 같은 UUID와 같은 본문을 사용한다. 오래된 탭·다른 질문 ID·내용이 달라진
재시도를 거부한다. 추가 답변을 고치면 revision이 바뀌고 동의를 다시 받는다. 최종 접수는
서버가 본문을 구성하며, 사진 저장과 두 감사 저널 기록을 같은 트랜잭션에서 처리한다.

감사 기록에는 질문 묶음 ID·버전·항목 상태만 남긴다. 답변 본문은 감사 메타데이터나 로그에
복사하지 않는다. 직접 식별자는 대화 저장·모델 맥락에 들어가기 전에 비식별 처리한다.

## 모델 담당자가 나중에 연결할 부분

현재 `choose_topic`은 시민의 선택이다. 키워드로 자동 분류하지 않는다. 질문 단계는 앱 서버가
진행하며 `questions` 단계나 임의 항목 요청을 기존 v2 모델에 보내지 않는다. 기존 모델 HTTP
계약은 유지하고, 안내 검색에 진입할 때 비식별 추가 답변을 포함한 초안·대화를 전달한다.

[별도 추출 계약](CHAT_EXTRACTION.md)은 등록된 template_id·원문과 같은 장소/답변·목적을
제안한다. 서버가 ID·항목·길이·인용·현재 기준을 검사하고 시민이 확인해야 반영한다.
`templates()`와 `IntakeState`를 재사용하며 확인한 답변은 `in_description`과 인용 값으로
보존한다. 이미 직접 선택한 상황의 질문 중간에는 추출을 호출하지 않는다. 공식 서비스 ID나
부서 배정을 대화 묶음 ID와 같은 것으로 취급하지 않는다. 실제 모델 연결·복합 요청·모호함의
평가는 후속 과제이며 기본은 꺼짐, 합성 모드는 예시 한 문장만 처리한다.

팀은 UI 담당이 모바일·키보드 과제를, 데이터 담당이 상황·문구 누락을, 서버 담당이 ID 검증과
실제 모델 연결을, 모델 담당이 자동 분류·정보 추출 평가를 맡으면 된다. 실제 사용자 평가는
[기존 과제 양식](CITIZEN_USABILITY_TEST.md)에 “이미 적은 답변”, “모름”, “복지 상담만 하기”,
“위험 답변”, “추가 답변 수정 후 접수”를 추가해서 진행한다.

## 검증 기록

새 질문 계약 테스트 28개를 포함한 전체 pytest 408개, Ruff 검사·포맷, mypy,
JavaScript 구문·diff 공백 검사를 통과했다. 12개 상황의 공통 항목 재사용, 세션 이어보기,
잘못된 ID·단계·길이 거부, 수정 후 오래된 동의 거부, 비식별 처리, 사진과 답변의 원자적 접수,
긴급 안내·재분류 때 복지 검토 유지가 포함된다. 기본 시연과 제공자 미연결 상황도 검사한다.

기존 합성 rules 평가 228개와 검색 평가 36개가 통과했다. 새 LLM의 분류·추출 성능을
측정한 결과는 아니다. 실제 브라우저의 추가 질문 → 수정 → 접수, 복지 안내만 하기,
320px·글자 200% 검증 결과는 [UI 기록](UI.md)을 참고한다. DB 스키마·의존성 추가는 없다.
