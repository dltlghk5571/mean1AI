## JSON을 다음 모델과 UI에 연결하는 방법

- `source_code`: 네 복지 사업의 화면에서 확인한 번호를 보관했다. 조직 코드도 실제 링크에서
  확인한 경우에만 채웠다. 원본 업무 분류 코드라고 해석하지 않는다.
- `pilot-service-*`, `pilot-category-*`, `pilot-org-*`, `pilot-work-*`: 프로젝트 내부 ID다.
  기존 `departments.json`의 배정 ID와 호환되지 않으며 승인해도 자동 교체되지 않는다.
- `work_assignments`: 동일 업무에 여러 후보를 연결하고 관할 문자열·미확정 경계를 함께 보관한다.
  현재 문자열은 검수 자료이며 주소를 자동 판정하는 공간 데이터나 `resolve_jurisdiction` 구현이 아니다.
- `required_information`: 44개의 **프로젝트 질문안**이다. 공식 법정 필수 항목이 아니므로 모두
  `required=false`로 두었다. 질문의 필수화·순서·조건은 팀 검수 후 새 버전에서 결정한다.
- 공식 내용과 질문안을 수동 요약했다. `fetched_at=null`, 실제 작성 시각은 `ingested_at`이다.
  `content_hash`는 저장한 요약의 해시이며, 서버 원본 응답의 무결성 증명이 아니다.
- 시행일이 확인되지 않아 `effective_from/until=null`이다. `retrieval_use`와 `training_use`는
  모두 `unknown`, 모든 업무는 `requires_human_review=true`다.

2026-09-08에 [상황별 질문](CITIZEN_QUESTIONS.md)을 챗봇에 연결했다. 공통 `content`,
`location_text`를 재사용하고 앱에서 작성한 질문 24개를 시민의 상황 선택에 따라 묻는다.
사진 준비 여부도 물을 수 있으며 실제 사진은 최종 확인 화면에서 선택한다. 공식 자료 승인과는
독립적이며, LLM의 상황 선택·항목 추출·지역 판정·새 서비스 ID 분류는 후속 구현이다.

다음 구현에서는 검수된 ID 집합을 분류 LLM에 전달하고 서버가 응답 ID를 검사한다. 사용자에게
부서를 고르게 하지 않는다. 이미 제공한 정보를 재질문하지 않고, 한 번에 하나씩 쉬운 질문을
묻는다. 모름·건너뛰기를 허용하며 위치·시설·범위가 불명확하면 배정을 보류한다. 안내 요청을
곧바로 민원으로 접수하지 않고, 제출 의사와 최종 요약 확인 후 시제품 내부 접수를 진행한다.

복지에서는 주민등록번호·계좌·진단서·장애 증명사진을 요구하지 않는다. 질문은 지원 주제,
구·동, 원하는 안내·신청 단계 중심으로 제한한다. 위험이 감지되면 질문 완료나 사진을 기다리게
하지 않고 기존 긴급 안내·사람 검토 흐름을 우선한다.

## 검수 화면과 수집 담당자의 다음 작업

1. 담당자 로그인 → `/staff/service-catalogs` → **생활불편·복지 대표 업무 12개 불러오기**.
2. 개수 확인 → **검수 대기로 등록**. 이때 시민 검색에는 공개되지 않는다.
3. 출처 요약, 조직·관할·미확정 경계, 질문의 필수·선택, 정책 날짜를 대조한다.
4. 표기 불일치·이용 조건 등을 확인한 결과는 새 버전 JSON에 기록한다. 승인 버튼은 이용 조건이
   미확인인 현재 후보에서는 비활성이다. 출처가 확인된 공개 버전은 이전 공개 전체를 대체한다.

[성남시 저작권 정책](https://www.seongnam.go.kr/cn050401)은 개별 자료의 공공누리 표시·조건을
확인하도록 안내하며, 표시 없는 자료 이용에는 별도 협의를 안내한다. 조회한 복지 상세 화면의
본문에서는 이용 유형 표시를 확인하지 못했다. 일반 정책 페이지가 존재한다는 이유만으로
일괄 `allowed`로 바꾸거나 학습 데이터를 추출하지 않는다.

브라우저로 확인한 복지 경로는 `/wf-pm020101`, 상세는 `/wf-pm020101/<사업번호>`이며
본문 영역은 `#contentLoad`였다. 조직도는 `/pm04041101`의 `deptCode`, `orgSelect`로
대상을 구분한다. 기존 수집기의 민원 경로·`contents` 선택자를 그대로 적용하면 안 된다.

수집 담당자는 다음 PR에서 경로별 허용 범위, robots, 이용 조건, 실제 HTML 추출을 검증한다.
목록의 303건과 수집 성공·실패·중복·누락을 대조하고, 본문 문의처·목록 담당 부서·조직도를
서로 다른 근거로 저장해 불일치를 검수 대기로 남긴다. 로그인·첨부 원문·내부 통신 API는
이번에 수집하지 않았고 네트워크 수집기의 비활성 상태도 유지한다.

복사하지 않으며 “배정 보류가 맞는 사례”를 오답으로 취급하지 않는다.

재현 가능한 명령과 담당별 과제로 정리한다. 이번 추가로 후보를 승인하거나 최신 사실로 갱신하지 않았다.

## 이번 구현의 검증 기록

- 전체 pytest 380개, Ruff 검사·포맷, mypy 통과. 미인증 후보 조회 차단, 불러오기만으로 DB에
  적재되지 않음, 검수 대기 등록의 감사 기록, 미확인 자료 공개 거부를 확인했다.
- 별도 로컬 DB에서 실제 버튼으로 후보 불러오기 → 검수 대기 등록을 수행했다. 업무 12개,
  분장 후보 32개, 질문 44개가 표시되고 두 보류 업무는 조직 미확인으로 보이며 공개 버튼은 비활성이다.
- 기본 데스크톱 화면과 320px 화면에서 표시를 확인했다. 화면 재배치 완료 후 가로 넘침이 없었다.
  검증용 탭·서버를 종료했으며 실제 시민 검색에 이 후보를 승인하지 않았다.
- 기존 합성 규칙 평가 228개·검색 평가 36개 통과. 이번 12개에 대한 새 LLM의 분류 성능이나
  실제 사용자·기관 검수 결과는 아직 없다.
