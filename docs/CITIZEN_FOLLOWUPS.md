# 기존 민원 추가 문의

AI 서버 없이 시민의 문의와 담당자 답변을 기존 접수번호 아래 이어서 남긴다. 새 민원을 만들거나
기존 민원의 분류·부서·처리 상태를 자동 변경하지 않는다. 실제 기관 접수·답변 발송과는 연결되지 않는다.

## 화면 흐름

1. 시민이 `내 민원 조회 → 민원 상세 → 추가 문의`에서 2~2,000자의 내용을 작성한다.
2. 전달 동의 후 저장한다. 내용을 수정하면 동의 체크가 해제된다. 문의에 사진을 추가하는 기능은 아직 없다.
3. 담당자는 `/staff/follow-ups`에서 미답변 문의를 확인한다. 기존 민원이 검토 완료 상태여도
   이 목록에 표시된다. 긴급도 높은 순서, 같은 긴급도에서는 오래 기다린 순서이며 페이지당 20건이다.
4. 검토 승인 역할(`reviewer`)이 5~4,000자의 답변을 직접 작성하고 공개를 승인한다.
   공개 답변은 시민 화면과 담당자 상세에 함께 표시되고, 해당 문의가 미답변 목록에서 빠진다.
5. 시민·담당자 상세의 문의 이력은 최신순, 페이지당 20건이다. 일반 민원 답변과 추가 문의 답변은
   별개이며, 문의에 답변했다고 기존 민원이 종결되거나 일반 답변이 교체되지 않는다.

작성 중 내용은 페이지 메모리에만 유지한다. 이동 시 브라우저 확인을 요청하지만 브라우저 종료·강제
새로고침에 대한 초안 복구를 보장하지 않는다. 전송 실패·시간 초과 시 입력을 유지하고 같은 요청을
재시도한다. 새로고침 링크는 실제 페이지를 다시 읽으며, 자동 새로고침·푸시·문자 알림은 없다.

## 접근과 저장

- 작성은 **처음 접수한 브라우저의 유효한 30일 시민 세션**에서만 가능하다. 접수번호·조회 코드로
  연결한 다른 세션의 `CitizenGrant`는 사진·문의·답변 조회만 허용한다. 기기 변경·세션 만료 후
  작성 권한을 복구하려면 향후 정식 본인확인 설계가 필요하다.
- 시민 POST는 `X-Citizen-CSRF`, 담당자 POST는 기존 역할 세션과 `X-CSRF-Token`을 검증한다.
  시민 문의는 프로세스 내 IP 해시 기준 분당 5회로 제한한다. 다중 프로세스의 공유 제한기는 후속 범위다.
- 저장 전 전화번호·이메일·주민등록번호 형식을 가린다. 이름·주소·모든 식별 가능한 문장을
  완전히 탐지하지 않으므로 합성 데이터로만 시연한다. 담당자 답변에 해당 형식이 남으면 공개를 거부한다.
- `citizen_followups`와 `citizen_followup_replies`를 추가한다. 기존 SQLite 테이블은 변경하지 않으며
  시작 시 `create_all`로 생성한다. 두 테이블은 UPDATE·DELETE 차단 트리거로 변경을 막는다.
- 문의는 원문 대신 가린 본문, 요청 UUID, 본문 재시도 검사용 HMAC, 긴급도·검토 사유를 저장한다.
  HMAC 키는 서버가 보관한 시민 CSRF 값이며 외부에 해시를 표시하지 않는다. 답변은 문의당 한 건의
  공개 스냅샷과 세션에서 얻은 담당자 ID를 저장한다. 공개 후 수정·정정 절차는 후속 범위다.
- 문의와 규칙 기반 안전 확인은 `citizen_followup_added`, 담당자의 공개 승인은
  `citizen_followup_reply_published` 감사 이벤트를 같은 트랜잭션으로 저장한다. 감사에는 본문을 넣지 않는다.
- 민원 행의 쓰기 잠금과 DB 유일성 제약으로 동시 저장을 직렬화한다. 동일한 요청 키·동일한 내용은
  기존 결과를 돌려준다. 이미 사용한 키의 내용이 달라지면 409다. 공개 답변도 같은 내용의 재전송은
  성공하고, 다른 답변으로 덮어쓰려는 요청은 409다. 저장과 감사 중 하나라도 실패하면 함께 롤백한다.
- 시민 응답은 허용한 필드만 렌더링한다. 원문·내부 초안·담당자 ID·해시·소유자 정보는 전달하지 않는다.
  기존 비공개 페이지의 `no-store`·`no-referrer` 정책을 따른다. 세션 만료는 DB 삭제가 아니다.

## HTTP 계약

JSON 문자열 필드만 허용하며 요청은 최대 160,000바이트, 알 수 없는 필드는 거부한다.
두 POST 모두 별도 확인 값 `confirmed: "yes"`가 필수다.

시민: `POST /minwon/{complaint_id}/follow-ups`

```json
{
  "request_key": "4e7f6fc7-ce0f-4091-bbf9-ae8aac25b37e",
  "body": "합성 문의: 현장 확인 일정이 궁금합니다.",
  "confirmed": "yes"
}
```

성공은 `200 {"redirect": "/minwon/<id>?saved=<followup_id>#followup-<followup_id>"}`다.
리다이렉트 주소는 저장한 문의를 포커스하며 새 문서를 읽는다. 중복 클릭·불확실한 전송 결과 재시도에는
같은 `request_key`와 같은 본문을 사용한다. 409가 나면 상세 화면에서 기존 기록부터 확인한다.

담당자: `POST /complaints/{complaint_id}/follow-ups/{followup_id}/reply`

```json
{
  "body": "합성 답변: 현장 확인 일정을 검토하고 있습니다.",
  "confirmed": "yes"
}
```

성공은 `200 {"saved": true}`다. 이후 상세 또는 대기 목록을 다시 읽는다. 조회 권한이 있는 모든
데모 담당자가 목록을 볼 수 있지만 공개는 검토 승인 역할만 가능하다. 민원과 문의 ID의 소속을 검증한다.

공통 오류: 403 세션·CSRF·역할, 404 접근 불가 또는 존재하지 않는 문의, 409 기존 저장 내용 충돌,
413 요청 크기, 422 글자 수·확인·필드/개인정보 검증, 429 시민 요청 제한, 503 저장 실패·불확실.
오류 응답은 본문을 되돌려주거나 예외 내용을 로그에 남기지 않는다.

## 안전 신호와 모델 연결 범위

기존 긴급 표현 탐지와 민감 분야 규칙을 추가 본문에도 적용한다. 자해·폭력 표현도 우선 확인 대상으로
표시한다. 탐지 규칙은 보조 신호이며 모든 위험을 찾아내지 못한다. 모든 문의는 담당자가 직접 검토한다.
긴급 표현에는 시민 화면에서 긴급 신고 경로를 안내하고, 담당자 대기 목록에서 먼저 표시한다.

분류 LLM·대화 모델·자동 답변·재분석·외부 발송은 호출하지 않는다. 추가 내용이 기존 AI 분류나
답변 초안에 자동 반영되지 않으므로 담당자는 문의 이력을 직접 확인해야 한다. 향후 모델에 연결할 때는
민원 전체 버전, 새 위험 신호, 승인 답변의 유효성, 개인정보 범위와 재검토 책임을 함께 설계해야 한다.

이 기능은 같은 시민이 상태를 묻기 위해 별도 접수를 만드는 상황을 줄이기 위한 것이다.
다른 시민의 유사 민원을 자동 병합하는 의미상 중복 판단이나 법적 재민원 절차를 구현한 것은 아니다.
